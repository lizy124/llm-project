# 第 9 章：全链路串联总结

本章把前面章节串起来，分别展示 `MooncakeConnectorV1` 的 Pull 模式和 `MooncakeLayerwiseConnector` 的 Push 模式。

## 9.1 Pull 模式总览

```text
用户请求
  │
  ▼
Proxy
  │
  ├── 发给 P 节点：do_remote_decode=True, max_tokens=1
  │
  ▼
P 节点 prefill
  │
  ├── 计算 prompt KV Cache
  ├── request_finished()
  │     ├── delay_free_blocks=True
  │     └── 返回 remote_block_ids / host / port / engine_id
  │
  ▼
Proxy
  │
  ├── 发给 D 节点：do_remote_prefill=True + P 侧 remote metadata
  │
  ▼
D 节点
  │
  ├── Scheduler 预分配本地 blocks
  ├── 请求进入 WAITING_FOR_REMOTE_KVS
  ├── Worker start_load_kv()
  ├── KVCacheRecvingThread 拉取 KV
  ├── 发送 DONE_RECVING_MSG 给 P
  ├── 请求恢复 WAITING/RUNNING
  └── Decode 继续生成
```

## 9.2 Pull 模式详细时序

### 阶段 1：初始化

```text
P / D Engine 启动
    │
    ├── register_connector()
    │       └── 注册 MooncakeConnectorV1 → MooncakeConnector
    │
    ├── MooncakeConnector(role=SCHEDULER)
    │       └── MooncakeConnectorScheduler
    │
    ├── MooncakeConnector(role=WORKER)
    │       └── MooncakeConnectorWorker
    │
    └── register_kv_caches(kv_caches)
            ├── 计算每层 KV Cache base_addr / block_len / stride
            ├── collect_storage_merged_register_regions()
            ├── global_te.register_buffer(...)
            ├── 构建 MooncakeAgentMetadata
            └── 按 kv_role 启动后台线程
                    ├── P: KVCacheSendingThread 监听 ZMQ ROUTER
                    └── D: KVCacheRecvingThread 等待拉取任务
```

### 阶段 2：Proxy 发起 P 侧 prefill

```text
Proxy
    │
    └── 请求 P 节点
            kv_transfer_params = {
                do_remote_decode: True,
                do_remote_prefill: False,
                transfer_id: ...,
            }
            max_tokens = 1
```

P 侧 Scheduler：

```text
get_num_new_matched_tokens()
    │
    ├── do_remote_prefill=False，不拉远端 KV
    ├── do_remote_decode=True 且需要截断时，删除 prompt 最后一个 token
    └── 返回 (0, False)
```

P Worker 执行 prefill，把 KV Cache 写入本地 NPU KV buffer。

### 阶段 3：P 侧 request_finished 返回 remote metadata

```text
request_finished(request, block_ids)
    │
    ├── 检查 do_remote_decode=True
    ├── 检查 request.status == FINISHED_LENGTH_CAPPED
    ├── _get_transfer_block_ids() 裁剪 prompt blocks
    ├── _get_swa_transfer_block_ids() 裁剪 SWA window
    ├── _reqs_need_send[req_id] = now
    └── 返回：
            delay_free_blocks = True
            kv_transfer_params = {
                do_remote_prefill: True,
                remote_block_ids,
                remote_engine_id,
                remote_request_id,
                remote_host,
                remote_port,
                remote_pcp_size,
                remote_dcp_size,
                remote_ptp_size,
                remote_multi_nodes_meta_mapping,
                num_prompt_blocks,
            }
```

P 侧 blocks 此时不能释放，必须等 D 侧拉取完成。

### 阶段 4：Proxy 发起 D 侧 decode

```text
Proxy
    │
    └── 请求 D 节点
            kv_transfer_params = P request_finished 返回的 dict
            do_remote_prefill = True
```

D 侧 Scheduler：

```text
get_num_new_matched_tokens()
    │
    ├── 识别 do_remote_prefill=True
    ├── actual = _state_prefill_token_count(prompt_len)
    ├── count = max(actual - num_computed_tokens, 0)
    └── 返回 (count, True)

allocate_slots(..., delay_cache_blocks=True)
    │
    ├── 分配本地 KV blocks
    └── request.status = WAITING_FOR_REMOTE_KVS

update_state_after_alloc()
    │
    ├── 保存 local_block_ids
    ├── 保存 remote kv_transfer_params
    └── _reqs_need_recv[req_id] = (...)

build_connector_meta()
    │
    └── meta.requests[req_id] = ReqMeta(...)
```

### 阶段 5：D Worker 拉取 KV

```text
start_load_kv(metadata)
    │
    ├── _get_kv_split_metadata()
    │       ├── 选择 P rank / handshake ports
    │       ├── 计算 local_block_ids_list
    │       └── 计算 remote_block_ids_list
    │
    ├── _get_group_pulls_metadata()
    │       └── 生成 GroupPull(group_id, tp_offset, pp_rank, ...)
    │
    └── kv_recv_thread.add_request(...)
```

接收线程：

```text
KVCacheRecvingThread._handle_request()
    │
    ├── _get_remote_metadata()
    │       ├── ZMQ → P: GET_META_MSG
    │       └── 得到 P KV base_addr / stride / te_rpc_port
    │
    ├── _transfer_kv_cache_all_groups()
    │       ├── 遍历 group_pulls
    │       ├── 计算每层 src/dst/length
    │       ├── batch_transfer_sync_read(session_id, src, dst, length)
    │       └── 必要时做 reformat / NZ / cat
    │
    ├── all_task_done 时 update_done_task_count(req_id)
    ├── 发送 DONE_RECVING_MSG 给 P
    └── request_queue.task_done()
```

### 阶段 6：P 侧释放 blocks

```text
P KVCacheSendingThread
    │
    ├── 收到 DONE_RECVING_MSG
    ├── remote_port_send_num 计数满足后
    └── task_tracker.update_done_task_count(req_id)

P Worker get_finished()
    │
    └── done_sending = {req_id}

Scheduler / Engine
    │
    └── 释放 request_finished 延迟的 KV blocks
```

### 阶段 7：D 请求继续 decode

```text
Scheduler 下个 step
    │
    ├── request.status == WAITING_FOR_REMOTE_KVS
    ├── _update_waiting_for_remote_kv(request) 返回 True
    ├── request.status = WAITING
    ├── 正常进入 RUNNING
    └── 使用已拉取的 KV Cache 继续 decode
```

## 9.3 Layerwise Push 模式总览

```text
用户请求
  │
  ▼
Proxy / metaserver
  │
  ├── 先让 D 节点预分配 blocks
  ├── D 把 remote_block_ids / host / port 发给 metaserver
  └── metaserver 转发给 P 节点

P 节点 prefill
  │
  ├── 每层 attention 完成后 save_kv_layer()
  ├── KVCacheSendingLayerThread 查询 D metadata
  ├── batch_transfer_sync_write() 写入 D KV Cache
  └── 最后一层完成后 DONE_SENDING_MSG

D 节点
  │
  ├── KVCacheRecvingLayerThread 监听 DONE_SENDING_MSG
  ├── get_finished() 返回 done_recving
  └── 请求恢复并继续 decode
```

## 9.4 Layerwise Push 详细时序

```text
D Scheduler
    │
    ├── do_remote_prefill=True
    ├── 分配 local_block_ids
    ├── _reqs_need_recv[req_id] = (...)
    ├── 通过 metaserver 发送：
    │       do_remote_decode=True
    │       remote_block_ids = D 本地 blocks
    │       remote_host / remote_port = D side-channel
    │       remote_cached_tokens = request.num_computed_tokens
    │
D Worker
    │
    └── KVCacheRecvingLayerThread 监听 GET_META / DONE_SENDING

P Scheduler
    │
    ├── 收到 do_remote_decode=True
    ├── update_state_after_alloc()
    │       └── _reqs_need_send_layerwise[req_id] = SendReqInfo(...)
    └── build_connector_meta()
            ├── 更新 local_computed_tokens
            ├── 更新 local_transferred_tokens
            └── chunk_finish 判断

P Worker
    │
    ├── start_load_kv()
    │       ├── _get_kv_split_metadata()
    │       ├── _get_kv_split_metadata_for_mamba()
    │       └── 生成每个 req 的发送 metadata
    │
    ├── save_kv_layer(layer0)
    │       └── KVCacheSendingLayerThread.batch_transfer_sync_write()
    ├── save_kv_layer(layer1)
    │       └── batch_transfer_sync_write()
    ├── ...
    └── save_kv_layer(last_layer)
            ├── batch_transfer_sync_write()
            └── send_done_send_signal(DONE_SENDING_MSG)

D Worker
    │
    ├── 收到 DONE_SENDING_MSG
    ├── update_done_task()
    └── get_finished() 返回 done_recving
```

## 9.5 两种模式的选择建议

| 场景 | 建议 |
|------|------|
| 想要路径简单、容易排查 | `MooncakeConnectorV1` pull |
| 希望 P prefill 和 KV 传输重叠 | `MooncakeLayerwiseConnector` push |
| 需要直接复用上游 disaggregated proxy 逻辑 | pull 更接近常见模式 |
| 非对称 TP / quant / NZ / hybrid 复杂场景 | 两者都要核对当前代码支持矩阵，优先用已有测试覆盖的配置 |

## 9.6 关键设计点总结

| 设计点 | 实现方式 |
|--------|----------|
| P/D 角色分离 | `kv_role=kv_producer/kv_consumer` |
| 调度层异步加载 | `get_num_new_matched_tokens()` 返回 `(count, True)` |
| 请求等待远端 KV | `RequestStatus.WAITING_FOR_REMOTE_KVS` |
| P 侧延迟释放 | `request_finished()` 返回 `delay_free_blocks=True` |
| 远端 metadata | `MooncakeAgentMetadata` + ZMQ `GET_META_MSG` |
| 点对点传输 | Mooncake `TransferEngine.batch_transfer_sync_read/write` |
| 完成确认 | `DONE_RECVING_MSG` 或 `DONE_SENDING_MSG` + ACK |
| 多 TP/PP/CP 映射 | `_get_remote_ranks_for_req()`、`_get_kv_split_metadata()`、`GroupPull` |
| Hybrid/Mamba/SWA | `GroupTransferInfo`、`kv_group2layeridx`、Mamba state 特殊地址计算 |
| 失败容错 | invalid block ids、failed request tracking、超时释放 |

## 9.7 排查问题时的关键观测点

1. **Proxy 参数是否正确**
   - P 请求必须带 `do_remote_decode=True`。
   - D 请求必须带 `do_remote_prefill=True` 和 P 返回的 remote fields。

2. **端口是否匹配**
   - P/D `kv_port` 是 side-channel 基址，不是每个 rank 的实际端口。
   - 实际端口会加 `tp_rank/pp_rank/pcp_rank` offset。

3. **TransferEngine 是否初始化成功**
   - `global_te.get_transfer_engine()` 是否成功。
   - `register_memory()` 是否返回 0。

4. **metadata 是否能取到**
   - D pull：D 能否向 P 发 `GET_META_MSG`。
   - P push：P 能否向 D 发 `GET_META_MSG`。

5. **block ids 是否对应**
   - `remote_block_ids` 来自 P 侧。
   - `local_block_ids` 来自 D 侧分配。
   - prefix cache 命中会导致两者数量不同，需要看映射逻辑。

6. **完成信号是否到达**
   - Pull：D 是否发出 `DONE_RECVING_MSG`。
   - Push：P 是否发出 `DONE_SENDING_MSG`。
   - ACK 是否返回。

7. **请求是否卡在 WAITING_FOR_REMOTE_KVS**
   - 如果卡住，优先检查 Worker `get_finished()` 是否返回 done_recving。
   - 再检查 transfer 线程是否记录 failed/invalid blocks。

## 9.8 与 documents/pool 的对应关系

| 池化文档概念 | P/D 分离对应概念 |
|--------------|------------------|
| `KVPoolScheduler.get_num_new_matched_tokens()` 查询外部池 | `MooncakeConnectorScheduler.get_num_new_matched_tokens()` 识别 remote prefill |
| `ReqMeta` 描述 Store get/put | `ReqMeta` 描述 remote/local block、host、port、engine |
| `KVCacheStoreRecvingThread` 从 Store get | `KVCacheRecvingThread` 从 P 节点 read |
| `KVCacheStoreSendingThread` put Store | Pull 模式无显式 put；P 侧只监听 metadata 和 DONE |
| `PoolKey` / hash | `remote_block_ids` / `kv_transfer_params` / handshake metadata |
| `wait_for_save()` 等待 Store put | P 侧延迟释放 + DONE_RECVING_MSG 确认 |
| Layerwise Store | Layerwise P→D push |
