# vllm-ascend P/D 分离架构总览（以 Mooncake 为例）

## 1. 背景与目标

P/D 分离（Prefill/Decode Disaggregation）把一次请求拆成两个阶段：

- **Prefill 节点（P 节点 / kv_producer）**：负责计算 prompt 的 KV Cache，通常更关注 TTFT 和大块 prefill 吞吐。
- **Decode 节点（D 节点 / kv_consumer）**：负责加载 P 节点已经算好的 KV Cache，然后继续 decode，通常更关注 TPOT。

在 vllm-ascend 中，Mooncake P2P 路径不是把 KV Cache 写入外部 Store，而是让 D 节点通过 Mooncake `TransferEngine` 直接读 / 或让 P 节点逐层写到 D 节点的 NPU KV Cache 内存。

核心目标：

- P、D 节点可以使用不同实例数和并行策略。
- P 侧算完 prompt 后，D 侧不用重复 prefill。
- KV Cache 在 NPU/RDMA 路径中点对点传输，避免经过持久化池化存储。
- 支持普通 Attention、MLA/GQA、Hybrid KV Cache、Mamba/SlidingWindow、部分非对称 TP 和 Layerwise push。

## 2. 与池化系统的区别

| 维度 | AscendStore 池化 | Mooncake P/D 分离 |
|------|------------------|-------------------|
| 核心目标 | 跨请求复用前缀 KV / 外部 KV 池 | P 节点和 D 节点拆分执行 |
| 底层组件 | `MooncakeDistributedStore` | `Mooncake TransferEngine` |
| 数据流 | Worker put/get 外部 Store | D pull P 内存，或 P layerwise push D 内存 |
| key 机制 | `PoolKey` + chunk hash | `kv_transfer_params` + remote block ids + handshake metadata |
| 是否依赖 Metadata Server | Store 路径依赖 | P2P 标准路径不依赖 Mooncake Store metadata server |
| 完成确认 | Store put/get 完成 | ZMQ side-channel `DONE_RECVING_MSG` / `DONE_SENDING_MSG` 确认 |

## 4. 两条 Mooncake P/D 路径

| 路径 | 连接器 | 方向 | 主要场景 |
|------|--------|------|----------|
| **Pull 模式** | `MooncakeConnectorV1` / `MooncakeConnector` | D 节点从 P 节点拉取 KV | 标准 P/D 分离；P 侧 prefill 完后，D 侧开始拉取 |
| **Layerwise Push 模式** | `MooncakeLayerwiseConnector` | P 节点逐层推送 KV 到 D 节点 | D 先预分配 KV，P prefill 过程中逐层传输，便于重叠计算和通信 |

本文档主线以当前代码中的 `mooncake_connector.py` 为主，也单独说明 `mooncake_layerwise_connector.py` 的 push 模式。

## 6. 核心数据流（一句话概括）

### 6.1 Prefill 侧

Proxy 把请求发给 P 节点并设置 `do_remote_decode=True`；P 节点完成 prefill 后，`request_finished()` 返回包含远端 block、host、port、engine_id 等信息的 `kv_transfer_params`，同时延迟释放相关 KV blocks。

### 6.2 Decode 侧

Proxy 把请求发给 D 节点并设置 `do_remote_prefill=True`，同时携带 P 节点返回的 `kv_transfer_params`；D Scheduler 为外部 KV 预分配 blocks，把请求置为 `WAITING_FOR_REMOTE_KVS`；Worker 的接收线程从 P 节点拉取 KV，完成后请求回到 `WAITING/RUNNING` 继续 decode。

### 6.3 完成确认

D 侧拉取完成后，通过 ZMQ side-channel 向 P 侧发送 `DONE_RECVING_MSG`。P 侧 `KVCacheSendingThread` 收到确认后标记请求完成，后续 `get_finished()` 让 Scheduler 释放延迟保留的 blocks。
