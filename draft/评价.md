  ## 任务 3：layerwise 支持范围与默认值

  ### 1. “仅支持 Memcache”与代码实际行为不一致，问题真实存在

  连接器只根据 use_layerwise 直接创建 scheduler/worker，并没有拒绝非 Memcache backend：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/ascend_store_connector.py:89
  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py:145

  代码实际区分的是：

  self.use_gva_layerwise = self.use_layerwise and self.backend_name == "memcache"

  也就是说：

  - memcache + use_layerwise：GVA layerwise；
  - mooncake/yuanrong + use_layerwise：仍然进入非 GVA、按 key 分层的路径。

  非 GVA 路径不是空壳，存在完整的 key-based 线程实现：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:1201
  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:1464
  - scheduler 在非 GVA layerwise 下也会按 layer 生成查询 key：/E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/
    kv_transfer/kv_pool/ascend_store/pool_scheduler.py:549

  因此，任务背景中“代码仍可进入非-GVA key-layerwise 分支”是正确的；但不能直接断言它“不支持”。准确说法应是：

  > 文档宣称仅支持 Memcache，但代码对 Mooncake/YuanRong 保留了可执行的 key-based layerwise 路径；当前缺少明确的支持承诺、拒绝校验或测
  > 试矩阵。

  ### 2. 默认值问题真实存在，但原任务表述混淆了两条路径

  GVA layout 默认值为：

  num_prefetch_layers = min(num_shared_buffers, 8)

  非 GVA key-based 路径则是：

  self.num_prefetch_layers = int(
      self._extra_config.get("layerwise_prefetch_layers", 1)

  所以正确结论是：

  - Memcache/GVA：默认 min(layerwise_num_shared_buffers, 8)；
  - 非 GVA key layerwise：默认 1；
  - 文档写成统一的 1，对 GVA 路径不正确；
  - 任务背景写成 “Memcache/GVA 路径的运行时默认值” 基本正确，但必须明确不是所有 layerwise 路径。

  ## 任务 6：ZMQ lookup 超时、异常与 socket 恢复

  ### 1. client 无界等待，问题明确存在

  LookupKeyClient.lookup() 发送后直接阻塞在 recv()：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_scheduler.py:1156

  没有 RCVTIMEO、SNDTIMEO 或 Poller。同时 scheduler 直接调用 client，没有捕获 RPC 异常：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_scheduler.py:561

  因此 server 不响应时确实可能长期阻塞 scheduler。

  ### 2. server 缺少请求级异常处理，问题明确存在

  server 循环对帧数量、整数转换、msgpack decode、lookup 和 send 都没有 try/except：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/ascend_store_connector.py:293

  例如畸形报文导致 all_frames[2] 或 decoder 抛异常后，后台线程直接退出。进程未必退出，但这个 REP server 将不再处理后续请求。

  ### 3. “lookup 异常会杀死 server”这一句不完全准确

  KVPoolWorker.lookup_scheduler() 本身已经捕获 backend/lookup 异常并返回 0：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py:2339

  因此：

  - backend exists() 异常：通常不会杀死 server；
  - decoder、帧格式、参数解码异常：会杀死 server 线程；
  - backend 异常返回 0 时，client 无法区分“真实 miss”和“服务端错误”。

  任务应将背景改为：

  > 请求解析异常可能终止 server 线程；backend lookup 异常目前被折叠为 0 命中，缺少可观测、可区分的错误协议。

  ### 4. socket 恢复和降级语义确实缺失

  当前 client 没有重建 socket 的逻辑，close() 也只是关闭：

  - /E:/lizy/code/vllm-project/vllm_ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_scheduler.py:1190

  REQ socket 在超时或异常后不能简单继续复用，任务要求重建 socket 是合理的。

  但验收标准中的“scheduler 能够继续重算”需要写得更明确：最一致的现有语义是 RPC 失败时返回 0 个外部命中，让 scheduler 走本地计算，而不
  是把异常继续抛到上层。当前 lookup_scheduler() 返回 0 时，get_num_new_matched_tokens() 会走无命中路径；若 client 直接抛异常，则并不会
  自动重算。

  另外，当前日志会记录 sample keys 或完整 key 列表，例如：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py:2383
  - backend 中也有 keys=%s 日志。

  所以“错误日志不能记录完整 hash payload”是合理且必要的验收项。

  现有测试只有正常 client 请求，没有超时、畸形报文、server 恢复测试：

  - /E:/lizy/code/vllm-project/vllm-ascend/tests/ut/distributed/ascend_store/test_pool_scheduler.py:569

  ## 任务 8：attention gate 队列等待与调度优化

  ### 1. 队列头阻塞的结构性前提真实存在

  每个 transfer thread 使用单个 FIFO queue.Queue，线程逐个调用 _handle_request()：

  - /E:/lizy/code/vllm-project/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:311
  - /E:/lizy/code/vllm-project/vllm-ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:496

  GVA load 请求会先等待 save-owner，再等待 attention gate：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:1545

  key-based layerwise 也有同样的顺序等待：

  - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/kv_transfer.py:1236

  因此“队头任务等待 gate 时，后续任务不能被处理”在结构上成立。

  ### 2. 两类依赖确实不同，任务拆分正确

  - prefetch_layer_map 产生 wait_for_save_layer，用于共享 buffer 复用；
  - attention_start_gate 等待 attention 计算流到达边界；
  - gate 的 wait() 最终会调用 NPU event 的 synchronize()：
      - /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/attention_fence.py:27

  任务要求分别测量 save-owner wait、gate wait、queue wait 和 backend transfer，技术上是正确的。

  ### 3. 但“存在可安全提前执行的任务”目前不能由代码直接证明

  当前提交逻辑是：

  - 第 0 层按 num_prefetch_layers 批量提交；
  - 后续每次提交一层；
  - 非当前层任务附带 attention gate。

  见 /E:/lizy/code/vllm-project/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py:1676。

  这证明存在潜在 head-of-line blocking，但不能仅凭静态代码证明后续任务经常比队头任务更早 ready，或者优化一定能改善 TTFT/吞吐。因此任务
  8 使用 “Investigation/P3” 是合适的；背景应继续使用“可能”“需要测量”，不应写成已确认的性能缺陷。

  当前代码没有 queue enqueue、dependency-ready、transfer-start、transfer-end 的时间戳或 profiler 标记，现有测试也主要验证 gate/save 正
  确性，没有性能时间线。

  ## 最终建议

  任务 3、6、8 都有代码依据，可以发布，但建议修改任务稿：

  1. 任务 3：把“仅 Memcache”改成“文档与实际可执行 backend 路径不一致”，并补充非 GVA prefetch_layers <= 0 的校验/潜在死锁。
  2. 任务 6：保留 P0，但区分“请求解析异常导致 server 线程退出”和“backend lookup 异常被折叠为 0”；明确 RPC 失败降级为 0 命中/本地重算。
  3. 任务 8：保留调查性质，不要预设一定存在优化收益；要求先提供可复现时间线，再决定是否改调度。
