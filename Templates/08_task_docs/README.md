# 08 — 任务试行规范与五文档归档

> 新任务先读 [任务开发、验证与归档规范（试行）](task_lifecycle_spec_draft.md)，执行期间使用五个主题工作目录，完成后形成五份归档文档。该文件是任务组织的统一依据，文件名中的 draft 为兼容已有引用保留。
> 会话需要重开、需让新会话零上下文接手时，按 [会话交接文档规范（试行）](handover_spec.md) 在任务根维护 `HANDOVER.md`。
> 本页保留归档文档职责速查；[skeleton/](skeleton/) 是归档骨架。工作目录按试行规范第 3 节建立，具体方法参考 [01_requirements](../01_requirements/how_to_analyze.md) ~ [07_pass_criteria](../07_pass_criteria/pass_criteria.md)。

## 2. 命名与目录约定

- **实例位置**：`Proposals/<专项>/<任务>/`，执行期间按五个主题目录组织；归档文档位于任务 `archive/`，采用上表命名。已有五文档归档可保持原位置。
- **任务资产**：脚本与配置放任务 `03_verification_scripts/`，运行证据放 `05_verification_process_and_results/runs/`；归档需要的证据整理至 `archive/evidence/`。不再强制放入 `assets/` 或 `Technical/`。
- **文档关系**：执行期间维护真实脚本文件。归档时，03 正文给索引，**选定脚本与配置全文内嵌在文末附录**；04 引用 03 说明操作，05 引用脚本、命令与证据。不要求执行中重复维护两份全文。
- **附录分部分**：【配置与拉起服务】和【测试相关】仍按原要求完整收录；【agent 专用】只在必要时填写，没有需要可省略。agent 辅助操作能通过明确描述或短命令可靠重建时不贴大段脚本；影响操作条件、时序或判定的必要实现才附全文。一次性补丁、探针、迁移及归档工具通常只作为过程材料留存，不因由 agent 执行就收录。详见 [试行规范 §8.1](task_lifecycle_spec_draft.md#81-03-的组成agent-部分按需)。
- **避免重复**：同一结论只在一处详述，其余用相对链接指向（见 [Templates/README.md §5](../README.md)）。
- **拉起脚本风格**：环境准备脚本只写两段——**先 `export`/`source`/`unset` 环境变量，再一条启动命令**（如 `vllm serve …`），不掺杂 `mkdir`/`echo`/清理/探活等脚手架；池后端起单独成脚本（通常 2 行）。
- **测试工具优先级**：**能用标准工具（如 aisbench 压测 / 命中统计）就用标准工具**；只有标准工具覆盖不了的特殊场景（如需精确时序控制、单请求中途取消等）才自写测试脚本。两者都在 03 附录给出（标准工具脚本 + 自写脚本）。

## 3. 每份文档的必填要素（速查）

- **01**：需求一句话；改动面清单；依赖/约束/风险；选定方案与理由；验收判据。→ 详见 [02_design](../02_design/how_to_design.md)
- **02**：PR 身份（链接/编号/分支/commit）；diff 走读；实现取舍；配对版本。→ 见 [02_design §3](../02_design/how_to_design.md)
- **03**：脚本清单（编号 / 用途 / 运行位置 / **指向附录的链接**）+ 关键调用与参数 + 与文档的对应关系 + **文末附录内嵌筛选后保留的脚本与配置全文**。→ 见 [06_test_method §5.6](../06_test_method/test_design.md)
- **04**：环境表；拉起命令；READY 判据；命中判据（正计数形态）。→ 见 [03_env_setup](../03_env_setup/env_setup_guide.md) / [05_vllm_launch](../05_vllm_launch/vllm_pool_launch.md)
- **05**：矩阵；原始数据表；统计（均值/区间）；A/B 对照；结论。→ 见 [06_test_method](../06_test_method/test_design.md) / [07_pass_criteria](../07_pass_criteria/pass_criteria.md)

## 4. 使用方法

1. 新任务按试行规范建立任务入口和五个工作目录，主题内部按需扩展。
2. 执行期间维护需求、代码记录、真实脚本、操作说明和逐次运行记录；临时探针放 `_scratch/`。
3. 归档时把 [skeleton/](skeleton/) 下五个骨架复制到任务 `archive/`，提炼稳定内容与关键证据，核对版本和相对链接；骨架中的示例按实际需要填写。
4. 任务结束时将可复用经验回写 [Templates/](../README.md) 对应章节。

## 5. 与既有分层的关系

| 区 | 与本规范的关系 |
|---|---|
| `Templates/01~07` | 提供需求、设计和验证的方法论参考 |
| `Proposals/<专项>/<任务>/` | 工作目录、任务专属脚本与证据、五文档归档 |
| `assets/` | 跨任务共享资产及既有历史资产 |
| `Technical/` | 可复用知识和长期技术记录；不强制分拆任务证据 |

## 6. 维护规则

沿用 [Templates/README.md §4](../README.md)：通用经验回写对应章节；某次任务的服务器信息放任务 04 和运行记录。试行反馈优先修订统一规范，其他入口同步引用，避免建立第二套组织规则。
