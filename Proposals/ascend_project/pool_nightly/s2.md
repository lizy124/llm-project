## 1. 四载体统一分工

| 场景 | 平台/拓扑 | 池 backend | layerwise | 准确的主要看护内容 |
|---|---|---|---|---|
| S1 | A3，PD 分离 | memcache | Producer 开启，Consumer 关闭 | MultiConnector、PD 传输、Prefill 逐层写池、AIME 精度 |
| **S2** | **A5，DP8×TP1** | **memcache** | **开启** | **A5 `device_urma`、逐层写入/热池读取、GPQA 精度、性能** |
| S3 | A3，DP4×TP4 | memcache | 开启 | A3 基础逐层热池读取、GPQA 精度、稳定性能哨兵 |
| S4 | A3，TP8、MTP3 | mooncake | 关闭 | 整块 KV 写入/读取、MTP3 acceptance、verify 开关、性能 |

S2 的独有价值是 A5、DP8×TP1 和 `device_urma`。它与 S3 都使用 Memcache layerwise，但硬件、协议和并行拓扑不同，因此不是重复用例：S2 发现 A5/URMA/DP8 特有回归，S3 提供 A3/SDMA/DP4×TP4 的稳定对照。

整体硬约束保持不变：不新增 test case、不新起模型服务、不新建 YAML、不修改 CI 注册和 runner；所有考题复用 S2 原有模型服务。

## 2. 原始用例职责

池化改造前，S2 只看护：

- A5 单机 8 卡；
- DP8×TP1 与 Expert Parallel；
- DeepSeek-V4 tokenizer/tool parser；
- FP8 KV cache 与 FP8 indexer KV；
- MTP1；
- GPQA 精度，baseline `87.4`、threshold `5`。

原 case #1 没有性能考题。同文件的 `83.50106007067137/0.95` 属于其他 MTP4 rejection-sampler case，不能作为 S2 池化性能基线。

## 3. 最终执行流

```text
启动 Memcache MetaService（5000/6000）
        ↓
启动 A5 DP8×TP1、MTP1 服务
        ↓
GPQA：以 miss 为主，正常计算并逐层写池，执行答案判分
        ↓
pool_warmup：1 条 prefix90 请求，写入共享长前缀
        ↓
perf：64 条同源请求，逐层加载池中长前缀并测吞吐
        ↓
停止服务和 MetaService，释放端口
```

三门考题分别承担：

| 考题 | 看护内容 |
|---|---|
| GPQA | A5 Memcache layerwise 写入存在时，模型答案精度不回退 |
| pool_warmup | 完成一次共享长前缀逐层写池，为正式性能考题建立热池 |
| perf | 看护 `lookup → hit → layerwise load → 跳过重复 Prefill` 的端到端性能 |

GPQA 是写路径精度，不证明池命中后的答案精度；prefix90 perf 看护读路径成功性和性能，但不判答案。严格的热池读路径答案精度仍需要带共享前缀的可判分数据。

## 4. A5 Memcache 配置

### 4.1 A5 环境

A5（950PR/950DT）已经明确支持 Memcache。当前 UB 形态使用：

```yaml
envs:
  PYTHONHASHSEED: "0"
  ASCEND_LOCAL_COMM_RES: '{"version":"1.3"}'
```

运行环境还需满足：

1. 安装 `memfabric-hybrid`、`memcache-hybrid` 和 A5 MemFabric kernel；
2. 容器具备 `/dev/ummu`、`/dev/uburma`、`/usr/bin/urma_admin`、`/lib/route.conf`、`/etc/hccl_rootinfo.json`、`/etc/hixlep`；
3. 按 A5 要求关闭 custom-op 签名校验；
4. 启动前清理残留 1GB/2MB huge pages；
5. 不给 DeepSeek-V4 配置尚不支持的 `kv_load_failure_policy=recompute`。

如果实际 runner 改为 UBOE，协议应同步切换为 `device_uboe`，并使用对应 `ASCEND_GLOBAL_RESOURCE_CONFIG`；当前方案按 A5 UB runner 固定为 `device_urma`。

### 4.2 Managed Memcache pool

```yaml
kv_pool:
  type: "memcache"
  meta_service_port: 5000
  config_store_port: 6000
  config:
    meta:
      ock.mmc.log_level: "info"
    local:
      ock.mmc.log_level: "info"
      ock.mmc.local_service.world_size: 256
      ock.mmc.local_service.protocol: "device_urma"
      ock.mmc.local_service.dram.size: "10GB"
```

单机 runner 为当前 case 生成 `mmc-meta.conf` 和 `mmc-local.conf`，启动/停止 MetaService，并向模型服务注入 `MMC_LOCAL_CONFIG_PATH`。DP8 下 `memcache_dp_init_barrier` 默认开启，八个 DP worker 会在 Store 初始化后同步。

`10GB` 是首跑容量配置。正式纳入基线前必须确认 GPQA 写入的无关 KV 不会导致 warmup 热点前缀在 perf 前被淘汰；若出现 eviction，应根据实测 KV 占用调整容量或考题顺序。

### 4.3 Connector

```yaml
- "--no-enable-prefix-caching"
- "--kv-transfer-config"
- '{"kv_connector":"AscendStoreConnector","kv_role":"kv_both","kv_connector_extra_config":{"backend":"memcache","lookup_rpc_port":"0","use_layerwise":true}}'
```

- `kv_both`：同一服务执行写池和读池；
- `backend=memcache`：使用 Memcache/URMA 数据通路；
- `use_layerwise=true`：逐层保存和加载 KV；
- `--no-enable-prefix-caching`：关闭本地 HBM prefix cache，使外部池成为共享前缀的唯一命中路径。

这些参数只加到 case #1，不能进入全文件共享 `_server_cmd`，避免改变其余五个非池化 case。

## 6. 有效运行判据

一次运行只有同时满足以下条件，才能用于确定性能 baseline：

1. GPQA 分数处于 `87.4 ± 5`；
2. MetaService、八个 LocalService 和 DP barrier 初始化正常；
3. GPQA 或 warmup 日志存在 layerwise save 证据；
4. warmup 成功，首次查询允许 miss；
5. perf 从第一条请求开始出现 `kvpool hit tokens > 0` 和 `need to load > 0`；
6. 多个 DP rank 都能读取同一个共享前缀，不出现 rank 隔离；
7. 没有 OOM、allocation failure、load/save failure 或异常 eviction；
8. case 结束后 MetaService 退出，5000/6000 端口释放；
9. A5 runner 中存在 prefix90 数据集，实际 token 数和命中档位已记录。

任一正式 perf 没有正命中，即使吞吐显示 PASS，也不能纳入池化基线。

## 8. 故障定位

| 现象 | 优先定位 |
|---|---|
| MetaService 起不来 | Memcache/MemFabric 依赖、A5 kernel、端口、签名校验 |
| LocalService 初始化失败 | `/dev/uburma` 等挂载、UB 路由、`device_urma`、`ASCEND_LOCAL_COMM_RES` |
| DP8 部分 rank 卡住 | `memcache_dp_init_barrier`、单 rank 初始化错误、DP CPU process group |
| GPQA 掉分 | FP8 KV/indexer、layerwise save 与 MTP1 交互；用同提交去池对照 |
| warmup 写入但 perf 全 miss | block hash、tokenizer 前缀、写入完成时刻、DP rank key 可见性 |
| 部分 DP rank 命中 | DP8 调度、LocalService 注册、key/rank 隔离 |
| 命中后请求失败 | layerwise load、KV layout、FP8 KV/indexer、URMA 传输 |
| S2 失败而 S3 正常 | A5、URMA、DP8 或 A5 镜像环境 |
| S2 与 S3 同时失败 | Memcache layerwise 或 AscendStoreConnector 公共回归 |
