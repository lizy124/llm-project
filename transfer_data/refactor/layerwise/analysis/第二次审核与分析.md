### 反指控 1：#14697 证伪（问题 4 的"事实对、结论错"）——验证：**成立，第一次审核结论有误**

第一次审核的担忧是：P1/P2 方案 `on_worker_ready`（LIFE）的等价性论证依赖 "`init_store` 末尾 `_register_buffers_if_needed` 补注册"，而 #14697 删除 `init_store`，论证前提可能消失。

本轮拉取 #14697.diff 逐块验证：

| #14697 声称 | diff 验证结果 |
|---|---|
| 删除 `MemcacheBackend.init_store()` | ✓ 属实（memcache_backend.py @@ -104,14 +104,6 整段删除） |
| 不触碰 `ensure_initialized` | ✓ 属实（diff 中无该方法） |
| `use_gva_layerwise` 双处定义保留（仅重排） | ✓ pool_worker 侧 `self.backend_name`/`self.use_gva_layerwise` 行保留；pool_scheduler 侧保留但 `self.backend_name` 属性降为局部变量 |
| `batch_is_exist` → `exists` 统一 | ✓ pool_scheduler `:274` 调用点替换 + UT 同步替换 |

关键代码事实（当前 main，memcache_backend.py:62-73）：

```python
def ensure_initialized(self):
    if self._store_initialized:
        return
    with self._store_init_lock:
        ...
        self.store = self._setup_store()
        self._store_initialized = True
        self._register_buffers_if_needed()   # ← 补注册直接挂在这里，不经 init_store
```

**等价性论证在 #14697 之后依然成立**：`ensure_initialized` 自身末尾即调用 `_register_buffers_if_needed`，不依赖被删除的 `init_store`。第一次审核的担忧基于方案文本字面引用（"init_store 末尾"），实际机制不受影响。

附带确认 `register_buffer` 的对称设计（:119-121）：

```python
def register_buffer(self, ptrs, sizes):
    self._pending_buffers = (list(ptrs), list(sizes))
    self._register_buffers_if_needed()
```

pending + 立即 flush 的设计使"先 register 后 init"与"先 init 后 register"两种顺序收敛到同一终态，LIFE 的顺序交换（`ensure_initialized` → `register_buffer` 改为 `register_buffer` → `on_worker_ready`）在缓冲注册语义上严格等价。

## 二、其自身的新问题（本轮新发现）

### 问题 1.【中】LIFE 存在 lazy_init 击穿缺口（两轮审核均未发现，本轮首次检出）

`on_worker_ready` 设计（p1/p2 §2.2）对 MemcacheBackend **无条件**调用 `ensure_initialized`，未 gate `_lazy_init`。

代码事实链：

```python
# 构造（memcache_backend.py:51）
self._lazy_init = lazy_init and _is_device_sdma()
# lazy_init 由 pool_worker._init_backend 传入（#14697 后）：
lazy_init=self.use_compress          # 仅 DSV4 压缩模型为 True

# exists 的惰性短路（:133-138）
if self._lazy_init and not self._store_initialized:
    return [0] * len(keys)            # init 前优雅降级为全 miss

# batch_get_key_info 同样短路（:143-149），返回空 list
```

受影响组合：**memcache + 非 layerwise + compress**（非 GVA 路径——注意这与 layerwise 收敛主体无关，恰是 PR-A 不应触碰的路径）：

| | 现 main | LIFE 后 |
|---|---|---|
| `:816` 特判 gate | `use_gva_layerwise` → 非 layerwise 不触发 | 删除特判，`on_worker_ready` 无条件 hook |
| store 初始化时机 | 首次传输时（`batch_alloc` 等内部 `ensure_initialized`） | worker 启动即强制 |
| device_sdma 未就绪场景 | 优雅短路，不崩溃 | `_setup_store` 失败 → worker 启动崩溃（lazy_init 机制要规避的正是此） |

p1/p2 的等价性论证只覆盖了两种情形：① mooncake/yuanrong 继承 no-op（零变化）② GVA 模式顺序交换（终态等价）。**漏了第三种：memcache + lazy_init + 非 layerwise**。

缓解因素（如实记录）：memcache + GVA layerwise + compress 组合在现 main 下同样被 `:816` 特判击穿（现状即如此），本缺口只影响**非 layerwise** 路径——即 PR-A 若不管此问题，会让一个"行为保持"的重构 PR 携带一处行为变更（init 时机提前 + 潜在崩溃面扩大）。

**修复（一行）**：

```python
def on_worker_ready(self) -> None:
    if self._lazy_init:
        return
    self.ensure_initialized()
```

且 PR-A 出口验证清单目前不含 compress 路径，无冒烟兜底——补一条 mooncake/memcache 非 layerwise + compress 验证，或 UT 覆盖 lazy_init 短路路径下 `on_worker_ready` 的 no-op 行为。

### 问题 2.【小】"浅克隆无历史"是事实错误

回应文档 §1 附行声称："commit 页仅返回 diff，提交信息未取到；浅克隆无历史"。

本地仓库历史完整可考：

```

```

提交信息原文（节选）："Remove dead code: Delete methods with no callers ... and state fields that are stored but never read (**use_compress**, need_truncate, keys_per_block_hash, block_keys, **etc.**)."

精确性备注：提交信息未逐字点名 `use_gva_layerwise`（由 "etc." 隐含），第一次审核"提交信息声称该字段 stored but never read"的表述略松但实质成立。该细节是"未核实"是**方法缺口**而非事实不可得，PR 描述可以引用。建议回应文档修正此行记录。

### 问题 3.【小】§3 "其 Preparer 恰好可以直接组合它"推测过强

抢先合入策略的 4 个论点中，论点 2（任务正当性）内嵌一个过强推测："我们的 GVASession 落地后，其 LayerwiseTransferPreparer 恰好可以直接组合它，rebase 后代码量预期更小"。

逻辑检验：Preparer 与 GVASession 职责重叠（GVA 解析 + 租约管理）——这正是第一次审核指出的"同一职责的两种封装"。职责重叠的两种可能结局是**取代**或**组合**，后者并非更可能。该承诺若写入 PR 描述并 @ 作者，会形成误导性预期。

**处置**：抢先合入策略不依赖此论点（论点 1 顺序正确性 / 论点 3 main 回归修复 / 论点 4 反向绑架的代价，三者独立成立且充分）。建议从 PR 描述删除该句，§3 保留论点 1/3/4 即可。

### 问题 4.【微】笔误与欠精确表述

- §1 #4 行内 "#14654 未触碰该方法"——PR 号笔误，应为 #14697
- §4 "use_gva_layerwise 行保留仅重排"欠精确：pool_scheduler 侧 `self.backend_name` 被降为局部变量，CAP 在该侧的替换需引用局部变量（单行适配，§4 适配点清单已实质覆盖，仅表述完善问题）
