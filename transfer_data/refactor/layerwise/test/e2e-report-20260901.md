## 1. 验证背景

### 1.1 被测 PR 内容

PR #15367 是 layerwise GVA 重构第一批(行为保持的重新封装),核心改动:

1. `use_gva_layerwise(use_layerwise, extra_config)` gate 收敛为 memcache 协议模块
   单点(backend 键/默认值/归一化内置),删除仓库内 4 份派生副本
   (worker / scheduler / layout / connector)
2. GVA key 构造集中于 `GVAKeyFactory`(协议模块内)
3. 注册表数据绑定:`backend_map` 增加 `layerwise_protocol` 字段,通用层经
   `get_layerwise_protocol` 中性解析,不再硬编码 `memcache` 字符串
4. connector 侧派生删除:`AscendStoreConnector.set_external_slot_release_waiter`
   的 gate 下沉至 `KVPoolWorker`(取代 #15291 热修的 connector 侧副本)

### 1.2 #14465 回归机制(验证项 1 的由来)

#14465 清理死代码时删除了 connector 侧 `use_gva_layerwise` 派生副本,但
`AscendStoreConnector.set_external_slot_release_waiter` 仍读它。调用链:

```
AscendMultiConnector.__init__
  └─ _configure_layerwise_reuse_completion()
       └─ 对每个子 connector 调用 set_external_slot_release_waiter(...)
            └─ AttributeError(connector 侧 flag 已不存在)
```

触发条件:MultiConnector(PD 分离部署)且子 connector 组合中包含
① layerwise buffer-reuse provider(MooncakeLayerwiseConnector /
SfaRemoteD2HConnector)与 ② AscendStoreConnector(sink)。单实例
kv_both 路径不经过此代码,因此 UT 与单实例冒烟均无法覆盖,必须真实
PD 拓扑实测。

### 1.3 验证清单与验收标准

来源 `server-validation.md`(与 #15307 清单 1/2/3 相同;验证项 1 关注点为
"gate 在 worker 侧"):

| # | 验证项 | 目的 | 验收标准 |
|---|---|---|---|
| 1 | MultiConnector PD 分离 | #14465 修复生效点实测 | 请求成功率 100%;初始化链路无 AttributeError |
| 2 | memcache layerwise 冒烟 | load 路径非零 gva 真环境对应面,排除静默失效 | `load_gvas valid_gvas>0`;`hit_check hit_tokens>0` |
| 3 | mooncake 非 layerwise 冒烟 | 通用路径零回归 | 与 main 基线行为一致;三维证据链通过 |

## 7. 过程问题与根因分析(7 项,均为测试基建,被测代码零改动)

### 7.1 子 connector engine_id 冲突(场景 1 首启失败)

- 现象:P 侧 worker 初始化失败
  `RuntimeError: Worker failed with error 'vllm.config.kv_transfer.KVTransferConfig()
  got multiple values for keyword argument 'engine_id''`
- 根因:vllm `MultiConnector._get_connector_classes_and_configs` 构造子配置时
  执行 `KVTransferConfig(**ktc, engine_id=ktc.get("engine_id", parent_engine_id))`,
  子 dict 自带 engine_id 时同名 kwarg 重复
- 处置:engine_id 上提至 MultiConnector 顶层("0"),两个子项均不写
- 教训:MultiConnector 子 connector dict 禁写 engine_id(父注入)

### 7.2 HBM 残留致二次启动失败

- 现象:`ValueError: Free memory on device (52.5/61.27 GiB) on startup is less
  than desired GPU memory utilization (0.9, 55.14 GiB)`
- 根因:7.1 崩溃后 worker 残余进程未退,占住约 2.6 GiB/卡
- 处置:清理 `from multiprocessing` 残余进程;流程补"每轮启动前清残留 +
  npu-smi 复查"铁律

### 7.3 场景 3 零回归判据误报

- 现象:初版判据 `grep "layerwise config: num_layers"` 命中 → 误报
  "unexpected layerwise activation"
- 根因:该日志行(pool_worker.py:445)在 worker 构造末尾**无条件打印**,
  与 backend / use_layerwise 无关
- 处置:零回归判据改为 layerwise 路径专属调试行缺席
  (`load_gvas:` pool_worker.py:1500、`hit_check:` pool_scheduler.py:389),
  重跑确认 0 命中
- 教训:判据日志必须先核对代码位置的触发条件

### 7.4 场景 2 MetaService 指标名不存在

- 现象:初版证据链取 `memcache_batch_get_successes_total` 恒 0
- 根因:memcache 1.2.0 无此指标名
- 处置:按实态指标 `memcache_query_successes_total` 判定,并补
  `hit_check hit_tokens>0` 判据形成双保险

### 7.5 判定脚本 pipefail 静默退出

- 现象:场景 1 判定首跑请求 3/3 后脚本 exit 1,无 FAIL 记录、无后续输出
- 根因:`set -Eeuo pipefail` 下 `PUT=$(grep ... | awk ...)`,grep 无匹配时
  管道退出码 1,赋值携带该退出码触发 `set -e` 静默终止
- 处置:求和改纯 awk(`awk '/re/ {s+=$2} END {print s+0}'`,无匹配仍 exit 0)

### 7.6 mooncake master 端口残留(场景 3 前置)

- 现象:新 master 报 `bind port: 9008 error: Address already in use`
- 根因:14:01 拉起的旧 master(PID 12705)未退
- 处置:显式按 PID `kill -9 12705`(纪律:禁 pkill 模糊匹配)后重启,
  50088/9008 探活通过

### 7.7 gsm8k-lite 路径不存在

- 现象:场景 1 初跑 `No such file or directory:
