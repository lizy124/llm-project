# 任务开发、验证与归档规范（试行）

状态：试行，自 2026-10-13 起用于新任务；用户已认可试用，保留原文件名以保持引用稳定。执行反馈用于后续修订。

原“Proposals 只放方案、不放证据”和“任务脚本及其他非 Markdown 资产必须统一放 assets”的限制即日起废除。任务目录与材料归属以本规范为准；机器、传输和共享服务器等技术纪律继续有效。已有目录不自动迁移。

适用：开发任务、PR 验证、缺陷复现、性能实验和由多个子任务组成的专项。

## 1. 目标与基本判断

一个任务在执行期间有结构清楚的工作目录，完成后形成内容稳定的归档。工作目录服务于开发和验证；归档服务于阅读、复现和查证。

用户认可的归档样板是 [pr16461_async_abort](../../Proposals/ascend_project/pr16461_async_abort/01_requirements_and_design.md)：五份文档形成完整阅读主线，关键脚本与配置全文整合在第三份文档中。这种归档形态继续保留。

本规范进一步约束：

1. 任务从开始就按五个主题组织，不等结束后再从散乱文件中拼装文档。
2. 给人使用的配置、启动命令和测试入口必须直接可读；agent 远程编排单独收纳。
3. 每次测试都能追溯到当时的代码、环境、脚本、配置和原始结果。
4. 归档经过筛选，明确哪些是正式内容、关键证据、辅助工具和临时过程材料。
5. 目录按实际需要扩展，避免为填模板制造无意义的文件和空目录。

## 2. 专项、任务、测试场景和运行轮次

| 层级 | 划分依据 | 示例 |
|---|---|---|
| 专项 | 一组相关目标的总入口 | KV Pool nightly、模型适配 |
| 任务 | 能独立说明目标、方案和验收结论 | 异步加载取消泄漏修复验证 |
| 测试场景 | 同一目标下不同条件或对照组 | PRE/POST、layerwise 开/关、64k/128k |
| 运行轮次 | 某个场景的一次实际执行 | 某日期、某机器上的第 1 次运行 |

任务目录采用稳定的语义名称，例如 `pr16461_async_abort`。机器编号、日期、重试次数一般作为运行信息，不作为拆分任务的首要依据。

同一问题换机器复验、增加一组负载，通常增加场景或运行记录。若目标、方案和验收已经可以独立成立，则拆为关联任务。一个任务可以关联多个 PR；纯验证任务可以没有自己的 PR。

专项入口只维护任务索引、关系和总体进度。每个任务只确定一个正式位置，其他专项通过链接引用，不复制一套材料。持续 nightly 按可独立验收的建设任务划分，日常运行作为运行记录维护。

## 3. 执行期间的目录

下面是完整形态。五个主题固定；主题内部按需创建，示例中的所有辅助目录不要求一次建齐。

```text
<task>/
├── README.md
├── 01_requirements_and_design/
│   └── README.md
├── 02_development_and_pr/
│   ├── README.md
│   └── patches/                         # 按需：精确补丁、无法用 commit 表达的改动
├── 03_verification_scripts/
│   ├── README.md
│   ├── config/                          # 完整配置；多场景时按场景建子目录
│   ├── launch/                          # 人直接阅读和执行的服务启动脚本
│   ├── tests/                           # 标准工具入口、自写测试、数据生成、结果统计
│   └── agent/                           # 可复用的远程编排、补丁、采证工具
├── 04_verification_env_and_launch/
│   └── README.md
├── 05_verification_process_and_results/
│   ├── README.md                        # 测试计划、运行索引、结果汇总和当前结论
│   └── runs/
│       └── 20261013_110_pre_01/
│           ├── README.md                # 本轮身份、命令、过程、状态与结果
│           ├── inputs/                  # 按需：本轮脚本、配置快照或精确版本记录
│           ├── raw/                     # 原始 JSON、指标、必要日志
│           └── derived/                 # 可由 raw 重算的统计结果
├── _scratch/                            # 临时探针、调试脚本、尝试和中间输出
└── archive/                             # 形成归档时创建，结构见第 8 节
```

任务根 README 只回答：任务是什么、当前做到哪一步、当前结论和限制是什么、下一步做什么、去哪里读和运行。用一张表链接五个主题及已形成的归档，不重复各章正文。

当前工作状态维护在任务根 README。有效脚本维护在 03；04 负责说明执行位置和顺序；05 负责测试计划与事实记录。避免在多个文件维护相互冲突的“当前版本”。

产品代码默认仍在其开发仓库中。02 记录仓库、分支、commit、工作区未提交差异和 PR；不把整份 vLLM/vLLM-Ascend 源码复制到任务目录。任务独有且无其他源码仓库承载的小段实现，可在 02 下按用途存放并说明。

## 4. 五个主题的职责

| 主题 | 必须回答的问题 | 不应混入的内容 |
|---|---|---|
| 01 需求与方案 | 为什么做；目标和非目标；选择什么方案；验收标准；关键风险和方案变更理由 | 全量调试流水账、未标注的旧方案 |
| 02 开发与 PR | 哪些文件如何改；为何这样改；代码版本和 PR；手动修改或替换方法；回退方法 | 整份第三方源码、agent 远程执行包装 |
| 03 验证脚本 | 有哪些配置和入口；各做什么；运行位置、参数、依赖和输出是什么 | 测试结果结论、一次性探针堆积 |
| 04 环境与操作 | 如何从明确的起点搭环境、准备目录、启动、确认就绪、运行测试、停止和恢复 | 重复维护脚本全文、只有机器名称没有搭建信息 |
| 05 过程与结果 | 计划怎么测；实际测了什么；原始数据和统计是什么；哪些结论成立、还有哪些限制 | 用预期结果代替实测、把不同版本的结果混算 |

纯验证任务的 02 写清被测代码与版本，不编造开发工作或 PR。未知信息标“未记录/待补”，并说明对复现或结论的影响。

### 4.1 04 必须能供人顺序执行

按以下顺序组织：

1. 环境身份与起点：机器、设备、镜像及标识、容器、依赖版本、源码版本、模型和数据位置。
2. 环境准备：建容器或使用已有容器的具体条件、安装与挂载、工作目录和日志目录准备。
3. 资源检查：设备空闲情况、端口检查等必要前置条件。
4. 配置和启动：先后端、再引擎；注明每条命令在宿主机还是容器中、前台还是后台执行。
5. 就绪与场景有效性：服务可访问、请求完成、目标功能命中是不同检查，分别给出判据。
6. 测试入口：引用 03 文件，给出实际工作目录、场景参数和结果位置。
7. 停止与恢复：按已记录的 PID、容器或明确服务身份操作；说明补丁、配置和资源如何恢复。

“已有旧容器”可以是本次测试起点，但若没有镜像身份或重建信息，必须标注复现限制，不能声称任意环境都可重建。

## 5. 脚本与配置的编写规则

### 5.1 面向人的启动脚本

启动脚本固定两段：第一段 `set`、`unset`、`source`、变量赋值与 `export`；第二段直接写出服务启动命令。允许必要注释和日志重定向。

- 关键参数显式可见，避免通过多层函数、循环拼接和嵌套 shell 隐藏实际命令。
- 一个脚本启动一个服务；MetaService、LocalService、vLLM、代理各有明确入口。
- 不在启动脚本内夹杂目录创建、清理、打补丁、后台编排、重试、等待或自动停止。
- 这些必要操作写在 04 的前置步骤，或由 `agent/` 脚本调用；简化启动脚本不等于遗漏运行条件。
- `.conf`、JSON、YAML、标准工具的 `config.py` 等配置完整存放于 `config/`，不可只给出引用路径却缺文件。
- 多配置差异较大时，用具名场景子目录区分；少量可调参数可集中放在脚本开头并注明默认值。
- 相对路径的起点必须明确，04 给出相应 `cd` 命令或脚本说明其自身定位方式。

### 5.2 测试脚本

- 标准工具能够覆盖的场景优先使用标准工具，例如 aisbench；提供工具来源、精确版本、配置和完整运行入口。
- 标准工具不能表达必要控制条件时编写自定义测试，说明覆盖缺口。不要为了凑齐工具而给每个任务强加无关压测。
- 数据生成与统计脚本同样属于测试所需材料，不因其自动运行就归为 agent 专用。
- 自写测试开头说明目标、输入、执行步骤、触发成功判据、输出和局限。保留真正需要的时序控制、异常处理和结果记录。
- 未触发目标场景、请求失败、采样缺失等情况必须可识别；“脚本退出码为 0”不自动等于功能验证通过。
- 结果计算方法必须可核对；需要复杂统计时保留对应脚本和版本。

### 5.3 agent 工具与临时材料

分类依据是用途，不是谁写了脚本。`repro.py` 即使由 agent 编写，也是正式测试入口；远程下发、容器编排、自动补丁等才属于 agent 工具。

- 可复用且确有用途的 agent 工具放 `03/agent/`，尽量调用正式脚本，避免复制第二套启动参数。
- 一次性探针和尝试放 `_scratch/`，不自动进入正式脚本清单或归档。
- 临时脚本成为必要测试或采证步骤时，先整理、说明并验证，再提升到对应正式目录。
- 同一用途只保留一个当前正式入口。历史版本通过版本记录或运行快照追溯，不用 `new/final/final2` 连续复制。

03 的索引至少给出：路径、用途、运行位置、输入/配置、输出、验证状态。状态明确区分“已编写”“已静态检查”“已实际运行”；不得把文档中重写但未经运行的版本说成已验证。

## 6. 测试的层次与证据

### 6.1 先有测试计划

05 的测试矩阵在执行前建立，至少包含：场景、对应需求或风险、对照组、代码和配置差异、工具、轮数、有效性判据、通过标准。

验收目标先在 01 定义，再映射为 05 的具体测试。一般操作说明在 04；某一轮实际运行命令、临时偏差和结果写入该轮记录。

测试集合根据任务选择：缺陷复现、正常路径回归、性能压力、边界场景等。未执行项明确标注，不因目录齐全而认定任务通过。

### 6.2 每次有效执行形成独立记录

每个运行目录至少记录：

| 类别 | 内容 |
|---|---|
| 身份 | 运行编号、时间及时区、机器/设备、镜像/容器、代码 commit 与补丁 |
| 输入 | 场景、配置、脚本版本、工具版本、数据版本或生成方式、关键参数 |
| 操作 | 工作目录、真实执行命令、执行顺序、与计划的偏差 |
| 原始输出 | 客户端结果、相关服务日志、指标及退出状态 |
| 判定 | 场景是否触发、有效轮次、通过/失败/未执行/无效/阻塞及原因 |
| 复算 | 指标单位、统计窗口、warmup 是否剔除、样本数、统计方法 |

运行输入用“可取得的精确 commit + 补丁”或文件快照固定。仅记录一个会继续修改的脚本路径不够；只有哈希却无法取得对应内容也不够。

配置或代码改变后，新建运行记录；不得覆盖原始结果。场景内含多轮请求时可以保存在同一运行下的结构化数据中，不要求每个请求都建目录。

A/B 对照明确列出实际差异。镜像、负载或运行条件同时变化时，应限制归因范围。统计只纳入满足预定有效性条件的样本；异常、失败或排除样本留下原因，避免只保留成功结果。

### 6.3 大文件与外部依赖

关键小体积原始数据直接留存；大日志可记录精确内网位置、大小、哈希和必要片段。说明采样范围、截断情况和访问限制，不能把摘要冒充完整原始数据。

模型、数据集和工具仓库不盲目整份复制，但必须记录精确来源和版本；任务自有生成器及关键配置要保留。无法取得的依赖标为复现缺口。

所有材料的传输仍遵守 [公共约束](../_common/common_constraints.md)，不因归档而上传公网。

## 7. 执行流程与状态

| 阶段 | 执行动作 | 进入下一阶段前应具备的内容 |
|---|---|---|
| 建立任务 | 确认归属和边界，建立入口与五个主题 | 明确目标、非目标、已有材料和待解问题 |
| 需求与方案 | 完善 01，建立 05 的测试计划 | 可检验的验收标准和明确的实验方法 |
| 开发或版本准备 | 更新 02，开发代码或固定被测版本 | 代码身份、实际改动和验证对象明确 |
| 验证准备 | 整理 03，完善 04 | 配置、依赖、脚本、操作顺序和判据可执行 |
| 执行验证 | 分场景运行，同步记入 05 | 原始结果、输入身份、失败原因和统计可追溯 |
| 形成结论 | 对照 01 的标准整理 05 | 结论、覆盖范围和未解决项明确 |
| 整理归档 | 提炼五份归档文档及关键证据 | 链接有效、全文齐全、版本一致、状态诚实 |

以上是产出依赖，不要求机械串行。探索结果可以促使需求、方案或测试计划修订；记录重要改变及理由，不覆盖旧运行的事实。

根 README 的任务状态建议使用：规划中、开发中、验证中、受阻、已结束。另列“验证结论”和“归档状态”，例如“已结束 / 部分通过 / 已归档”。归档表示材料已整理，不等于验证通过。

阶段检查是 agent 的自检，不自动增加逐阶段向用户请示的流程。缺少会影响正确执行的必要信息时再澄清，其余在已授权范围内推进。

## 8. 完成后的归档

默认在同一任务内形成 `archive/`，保留用户认可的五文档结构：

```text
archive/
├── 01_requirements_and_design.md
├── 02_development_and_pr.md
├── 03_verification_scripts.md
├── 04_verification_env_and_launch.md
├── 05_verification_process_and_results.md
└── evidence/                            # 有必要原始证据时保留
    └── <run_id>/
```

这五份文档是相应工作目录的稳定提炼版。任务根 README 负责归档入口、归档日期和覆盖范围，不要求为归档另加一套重复导航。

### 8.1 03 的固定三部分

1. 配置与拉起服务：完整配置、后端和引擎启动脚本。
2. 测试相关：标准工具运行入口及必要配置、自定义测试、数据生成和必要统计脚本。
3. agent 专用：经筛选仍值得保留的远程操作和取证工具；没有就注明本任务无需保留。

正文给索引和用途，附录给保留文件的完整文本。每个代码块注明文件名、运行位置和必要参数。04 引用这些附录，给出可照着执行的步骤。

归档收录最终选定、确实支撑结论的脚本版本。仅作格式整理可以核对内容等价性；若修改了行为但未重跑，标明“整理后未复验”，保留实际运行版本的追溯信息。

### 8.2 归档取舍

| 材料 | 处理 |
|---|---|
| 最终需求、方案、开发说明、操作和结论 | 提炼到五份文档 |
| 正式配置、启动和测试脚本 | 全文整合进 03；需要直接执行时可保留工作目录中的对应文件 |
| 支撑结论的原始数据和关键失败证据 | 留存于 evidence，05 给出索引和统计 |
| 有解释价值的废弃方案或失败尝试 | 保留结论与原因；必要证据归入相应运行 |
| 有复用价值的 agent 工具 | 筛选后进入 03 第三部分 |
| 一次性探针、重复日志、临时调试和聊天记录 | 不进入正式归档；是否清理原件另行按迁移规则处理 |
| 可由精确版本重新取得的第三方源码、依赖缓存 | 留身份与取得方式，不作为任务交付物复制 |

“不进入归档”不等于删除原文件。关键失败证据不能因为测试未通过而丢弃。

### 8.3 工作目录与归档的一致性

执行期间，以工作目录文件为准，不要求每次改脚本都手工同步一份长篇归档。归档时从选定版本提取全文并核对；归档后将其视为有日期和范围的快照。

归档应能独立解释结论并支撑声明的复现范围。关键证据不要只链接到将来可能清理的 `_scratch/` 或活动运行目录；不可复制的大依赖使用精确、可取得的外部引用并说明限制。

补测仍使用新的运行编号；需要更新归档时明确新增范围、日期和结论变化。重大目标变更另立关联任务，避免悄悄改变原任务的含义。

已经存在、以五份文档直接置于根目录的稳定归档可保持原样，例如 `pr16461_async_abort`。不为统一外观强行包一层新目录。

## 9. 归档自检

- 从 01 的每项验收标准，能定位到 05 的测试或未覆盖说明。
- 从 05 的结论，能定位到有效运行、关键原始数据和统计方法。
- 从实际运行，能取得对应代码、脚本、配置和数据身份。
- 03 的配置和脚本全文完整，04 的环境准备与调用不依赖隐藏步骤。

## 11. 后续整理整个 Proposals 的方式

1. 先列任务清单：原位置、目标、当前状态、正式入口、相关代码、脚本、证据与外部引用。
2. 按内容识别专项和独立任务；目录名相似不等于同一任务，机器或日期不同也不一定是新任务。
3. 给每个独立任务确定唯一目标位置和材料分类。缺少证据就标缺口，不补造历史过程。
4. 先选一个活跃任务试用工作目录，再选一个已结束任务验证归档规则；复核阅读与执行体验后推广。
5. 分批整理。先处理有明确归属的材料，保留原路径到新路径的映射，同步修正文档引用。
6. 迁移前检查未提交改动；尊重已有用户修改，不做整库覆盖、reset 或批量删除。
7. 确认新入口和证据完整后，旧位置可改为迁移说明或按已授权范围清理；不长期维护两份当前版本。

预期效果：同类任务的目录、脚本和记录方式可预测；阅读者先看到正式方案、可执行入口和结论，需要时再进入运行证据与 agent 辅助材料。
