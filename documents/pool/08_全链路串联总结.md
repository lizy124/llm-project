# 第 8 章：全链路串联总结

本章将前面各章节的知识串联起来，完整展示一个请求从进入系统到 KV Cache 被存储、再到被另一个请求复用的全链路。

## 8.1 两大场景总览

### 场景 A：生产并存储 KV Cache（kv_producer 角色）

```
请求到达 → Prefill 计算 → KV Cache 存入 Mooncake Store
```

### 场景 B：复用已存储的 KV Cache（kv_consumer 角色）

```
请求到达 → 查询 Mooncake Store → 加载已缓存的 KV Cache → 只计算未命中的剩余 token
```

## 8.2 场景 A 完整链路：存 KV Cache

### 步骤 1：系统初始化

```
程序启动
    │
    ├── register_connector() 注册 AscendStoreConnector
    │
    ├── AscendStoreConnector.__init__(role=WORKER)
    │       └── KVPoolWorker.__init__()
    │               ├── 读取并行配置 (TP/PP/PCP/DCP)
    │               ├── 计算 block_size / hash_block_size / lcm_block_size
    │               ├── 创建 KeyMetadata 列表
    │               ├── 创建 ChunkedTokenDatabase
    │               └── 创建 MooncakeBackend
    │                       ├── 从 MOONCAKE_CONFIG_PATH 加载配置
    │                       ├── 初始化 TransferEngine（全局单例）
    │                       └── MooncakeDistributedStore.setup()
    │
    ├── AscendStoreConnector.__init__(role=SCHEDULER)
    │       └── KVPoolScheduler.__init__()
    │               ├── 计算 cache_transfer_granularity
    │               ├── 创建 LookupKeyClient（ZMQ 客户端）
    │               └── 初始化各种状态追踪字典
    │
    └── register_kv_caches(kv_caches)
            ├── 收集所有 KV Cache 张量的 base_addr/block_len/block_stride
            ├── ChunkedTokenDatabase.set_group_buffers(...)
            ├── MooncakeBackend.register_buffer(ptrs, lengths)
            │       └── TransferEngine.register_memory(ptr, size)
            └── 启动 KVCacheStoreSendingThread
```

### 步骤 2：请求调度与预填充

```
新请求到达 Scheduler
    │
    ├── get_num_new_matched_tokens(request, num_computed_tokens)
    │       │  (kv_producer 不做外部查询，因为它是生产者)
    │       └── 返回 (0, False)
    │
    ├── Scheduler 分配 KV Cache blocks
    │
    ├── update_state_after_alloc(request, blocks, num_external_tokens)
    │       │  (num_external_tokens == 0，因为没有外部命中)
    │       └── 记录到 _unfinished_requests
    │
    └── build_connector_meta(scheduler_output)
            │
            └── 创建 ReqMeta：
                    can_save = True   （需要保存）
                    load_spec = None  （不需要加载）
                    token_len_chunk = num_tokens_to_save
                    block_ids_by_group = allocated_block_ids
                    block_hashes = request.block_hashes
```

### 步骤 3：推理执行 & KV Cache 存储

```
推理步骤结束
    │
    └── wait_for_save()
            │
            ├── 创建 NPU Event（记录当前 NPU 状态）
            │
            ├── 遍历 metadata.requests
            │       │
            │       ├── add_stored_request(req_id)  # 计数 +1
            │       └── kv_send_thread.add_request(req_meta)  # 放入队列
            │
            ├── request_queue.join()  # ★ 阻塞等待
            │       │
            │       ▼  (KVCacheStoreSendingThread 后台线程)
            │
            │   _handle_request(req_meta):
            │       │
            │       │ 遍历每个 KV Cache 组 (group_id):
            │       │
            │       ├── process_tokens_with_block_ids(token_len, block_hashes, block_ids)
            │       │       生成: (start=0, end=128, key="DeepSeek-V4@...@hash_0")
            │       │             (start=128, end=256, key="DeepSeek-V4@...@hash_1")
            │       │             ...
            │       │
            │       ├── TP 分片 (self.tp_rank % self.put_step)
            │       │       只保留属于当前 TP rank 的 block
            │       │
            │       ├── exists(keys) 去重检查
            │       │       过滤掉 Mooncake Store 中已存在的 key
            │       │
            │       ├── prepare_value(start, end, block_ids)
            │       │       addr = k_base + block_id * k_stride
            │       │       size = block_len * (end-start) / block_size
            │       │
            │       ├── current_event.synchronize()
            │       │       ★ 确保 NPU 计算完成，KV Cache 数据已刷新到显存
            │       │
            │       └── m_store.put(keys, addrs, sizes)
            │               │
            │               ▼  MooncakeBackend.put()
            │               │
            │               ▼  MooncakeDistributedStore.batch_put_from_multi_buffers()
            │                       │
            │                       ├── 根据 key hash 选择存储节点
            │                       ├── TransferEngine 传输数据 (RDMA)
            │                       ├── 写入目标节点 CPU 内存
            │                       ├── (可选) 写入 SSD
            │                       └── Metadata Server 记录 key → 位置映射
            │
            └── 返回（所有 put 完成，请求可标记为 finished）
```

## 8.3 场景 B 完整链路：取 KV Cache

### 步骤 1：系统初始化（同场景 A，但角色为 kv_consumer）

与场景 A 基本相同，但额外启动：
- `LookupKeyServer`（ZMQ REP 服务端，处理 Scheduler 的查询请求）
- `KVCacheStoreRecvingThread`（如果 `load_async=True`）

### 步骤 2：请求到达，查询外部池

```
新请求到达 Scheduler（与之前存储的请求有相同前缀）
    │
    ├── ☆ get_num_new_matched_tokens(request, num_computed_tokens)
    │       │
    │       ├── 对齐到 cache_transfer_granularity (如 16384)
    │       │
    │       ├── LookupKeyClient.lookup(token_len, block_hashes, kv_cache_group_ids)
    │       │       │
    │       │       │  ZMQ REQ → Worker rank 0 的 LookupKeyServer
    │       │       │
    │       │       ▼  LookupKeyServer.process_request()
    │       │       │
    │       │       ▼  pool_worker.lookup_scheduler()
    │       │               │
    │       │               ├── process_tokens() 按当前 rank / 当前 group 生成 key
    │       │               ├── hybrid 场景筛选 lookup gate group
    │       │               ├── m_store.exists(keys)
    │       │               │       └── MooncakeDistributedStore.batch_is_exist()
    │       │               │               └── 查询 Metadata Server
    │       │               │
    │       │               └── 找到最大连续 hit 位置，对齐到 granularity
    │       │
    │       └── 返回 num_external_hit_tokens (如 16000)
    │
    ├── 计算 need_to_allocate = 16000 - num_computed_tokens
    │
    ├── 创建 LoadSpec:
    │       vllm_cached_tokens = num_computed_tokens
    │       kvpool_cached_tokens = 16000
    │       can_load = False  (等待分配 block 后设为 True)
    │
    └── 返回 (need_to_allocate, is_async)
```

### 步骤 3：分配 block 并启用加载

```
    ├── Scheduler 分配 KV Cache blocks (约 16000/128 = 125 个 blocks)
    │
    ├── update_state_after_alloc(request, blocks, num_external_tokens=16000)
    │       │
    │       ├── num_external_tokens == kvpool_cached - vllm_cached  ✓
    │       └── load_specs[req_id].can_load = True  ★
    │
    └── build_connector_meta(scheduler_output)
            │
            └── 创建 ReqMeta：
                    can_save = False  (不需要保存，consumer 角色)
                    load_spec = LoadSpec(
                        vllm_cached_tokens=0,
                        kvpool_cached_tokens=16000,
                        can_load=True,      ★
                        token_len=16000,
                    )
                    block_ids_by_group = allocated_block_ids
                    block_hashes = request.block_hashes
```

### 步骤 4：加载 KV Cache

```
推理步骤开始
    │
    └── start_load_kv(forward_context)
            │
            ├── 遍历 metadata.requests
            │       │
            │       ├── 检查 load_spec.can_load == True ✓
            │       │
            │       ├── 确定 token_len = 16000
            │       │
            │       └── 选择加载模式：
            │               │
            │               ├── [load_async=True]
            │               │       kv_recv_thread.add_request(req_meta)
            │               │           │
            │               │           ▼  KVCacheStoreRecvingThread._handle_request()
            │               │               │
            │               │               ├── process_tokens_with_block_ids()
            │               │               │       (start, end, key, block_id)
            │               │               │
            │               │               ├── prepare_value()
            │               │               │       计算目标 NPU 内存地址
            │               │               │
            │               │               ├── TP 轮转 key/addr/size
            │               │               │
            │               │               └── ★ m_store.get(keys, addrs, sizes)
            │               │                       │
            │               │                       ▼  MooncakeBackend.get()
            │               │                       │
            │               │                       ▼  MooncakeDistributedStore
            │               │                          .batch_get_into_multi_buffers()
            │               │                               │
            │               │                               ├── Metadata Server 查询 key 位置
            │               │                               ├── TransferEngine RDMA 传输
            │               │                               │   到目标 NPU 内存地址
            │               │                               └── 返回状态码
            │               │
            │               └── [load_async=False, 同步模式]
            │                       │
            │                       ├── 同上生成 key/addr/size
            │                       └── m_store.get(keys, addrs, sizes)
            │                               (同步等待结果)
            │
            └── 加载完成，KV Cache 已在本地 NPU 显存中
    
推理继续执行（复用已命中的前缀 KV，只计算剩余 token；完全命中时仍保留至少 1 个 token 进入计算，避免 decode 阶段无输入）
```

## 8.4 两大场景在同一个集群中协同工作

在实际部署中，通常有以下角色分配：

```

│     Store            │  共享存储 │  3. 计算剩余 token   │

            │                              │
            └──────────┬───────────────────┘
                       │
            ┌──────────▼──────────┐
            │   Mooncake Store    │
            │  ┌──────────────┐   │
            │  │ Metadata     │   │  (Redis/etc.)
            │  │ Server       │   │
            │  ├──────────────┤   │
```

## 8.5 关键数据流时序图（一个请求的生命周期）

```
时间轴
  │
  │  系统启动
  │  ├── Connector 注册
  │  ├── KVPoolScheduler / KVPoolWorker 初始化
  │  ├── MooncakeBackend 初始化 (Store setup)
  │  ├── register_kv_caches (注册 NPU 内存)
  │  └── 后台线程启动
  │
  │  请求 A 到达 (生产者)
  │  ├── Scheduler: get_num_new_matched_tokens → 0 (无外部命中)
  │  ├── Scheduler: 分配 block
  │  ├── Scheduler: build_connector_meta → 标记 can_save=True
  │  ├── Worker: Prefill 计算 → 生成 KV Cache 在 NPU 显存
  │  ├── Worker: wait_for_save
  │  │   ├── NPU Event record
  │  │   ├── SendingThread._handle_request
  │  │   │   ├── process_tokens → 生成 key
  │  │   │   ├── exists() → 去重
  │  │   │   ├── prepare_value → 计算地址
  │  │   │   ├── synchronize() → 确保计算完成
  │  │   │   └── put() → 写入 Mooncake Store  ★
  │  │   └── request_queue.join() → 等待完成
  │  └── 请求 A 标记为 finished
  │
  │  请求 B 到达 (消费者，与 A 有相同前缀)
  │  ├── Scheduler: get_num_new_matched_tokens
  │  │   ├── ZMQ → LookupKeyServer → lookup_scheduler()
  │  │   │   ├── process_tokens → 按当前 rank / 当前 group 生成 key
  │  │   │   ├── hybrid 场景筛选 lookup gate group
  │  │   │   ├── exists(keys) → 查询 Mooncake Store  ★
  │  │   │   └── 返回 hit=16000
  │  │   └── need_to_allocate = 16000
  │  ├── Scheduler: 分配 125 个 blocks
  │  ├── Scheduler: update_state_after_alloc → can_load=True
  │  ├── Scheduler: build_connector_meta → 标记 load_spec
  │  ├── Worker: start_load_kv
  │  │   ├── RecvingThread._handle_request
  │  │   │   ├── process_tokens → 生成 key
  │  │   │   ├── prepare_value → 计算地址
  │  │   │   └── get() → 从 Mooncake Store 读取  ★
  │  │   └── KV Cache 已恢复到 NPU 显存
  │  ├── Worker: 复用已命中的前缀 KV，只计算剩余 token
  │  └── 请求 B 标记为 finished
  │
  ▼
```

## 8.6 Hybrid/Mamba 场景下的 block 延迟释放

在 hybrid KV cache 场景中，如果请求需要保存 Mamba / align-state 相关 group，Scheduler 不能在请求结束后立刻释放这些非空 blocks。当前实现会通过 worker metadata 做延迟释放：

```
Scheduler build_connector_meta()
    │
    ├── touch_sending_mamba_blocks(req_meta)
    │       ├── 为本次保存分配 event_id
    │       ├── 找出 Mamba group 中 block_id > 0 的 blocks
    │       ├── BlockPool.touch(...) 增加引用，防止保存期间被复用
    │       └── 在 sending_events / sending_blocks 中记录 event_id → block_ids
    │
Worker wait_for_save() / SendingThread._handle_request()
    │
    ├── 保存完成后 mark_completed_events(event_id)
    │
Worker build_connector_worker_meta()
    │
    └── 返回 AscendStoreKVConnectorWorkerMetadata(completed_events)

Scheduler update_connector_output()
    │
    ├── 聚合各 worker 上报的 completed_events
    └── 当完成数达到 world_size 后，BlockPool.free_blocks(...) 释放对应 blocks
```

这个机制避免了异步保存还没结束时，Mamba / hybrid 辅助 blocks 被提前释放并复用。

## 8.7 核心设计理念总结

| 设计理念 | 实现方式 |
|---------|---------|
| **Scheduler/Worker 分离** | AscendStoreConnector 根据 role 分发到 KVPoolScheduler / KVPoolWorker |
| **异步 I/O** | 后台传输线程 (KVCacheStoreSendingThread / KVCacheStoreRecvingThread) |
| **去重存储** | put 前先 exists 检查，避免重复写入 |
| **rank 感知** | Key 中包含 head_or_tp_rank、pp_rank；lookup 按当前 rank 生成 key，hybrid 场景筛选 gate group |
| **压缩组支持** | cache_family (c1/c4/c128) 控制 block_size 缩放和传输粒度对齐 |
| **混合 Attention** | 支持 FullAttention + Mamba + SlidingWindow 等混合同一模型 |
| **Mamba block 安全释放** | 保存期间 touch 非空 Mamba blocks，等待 worker metadata 上报完成后再 free |
| **可插拔后端** | Backend 抽象基类支持 Mooncake / Memcache / 元戎 等多种后端切换 |
| **懒初始化** | 压缩模型 + fabric memory 场景下，Store 延迟到首次 put 时初始化 |
| **失败容错** | 单个 block 加载失败不阻塞整体流程，记录到 _invalid_block_ids |
| **Layerwise 流水线** | 逐层存储/加载，层间重叠 I/O 和计算 |
