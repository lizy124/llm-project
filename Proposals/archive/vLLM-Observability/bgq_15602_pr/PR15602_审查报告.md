## 三、问题详述

### P1-1 / P1-2：延迟释放指标核心链路失效（高严重度）

这是本 PR 最核心的问题。**新增的 `update_finished_sending` 调用是空操作，`delayed_release_*` Gauge 无法表达其文档声称的语义。**

#### 证据链

`pool_scheduler.py` 的 `build_connector_meta`（PR 分支，约 L833-856）在**快照 meta 之前**就清理了延迟释放标记：

```python
# build_connector_meta 内：
for finished_req_id in scheduler_output.finished_req_ids:
    self._request_trackers.pop(finished_req_id, None)
    ...
    self._set_delayed_free(finished_req_id, 0)   # ← 先清理

for req_id in scheduler_output.preempted_req_ids:
    ...
    self._set_delayed_free(req_id, 0)            # ← preempted 也清理

meta = AscendConnectorMetadata(
    scheduler_output.preempted_req_ids,
    self._loading_req_ids.copy(),
    self._delayed_free_req_ids.copy(),           # ← 此时恒为空集
)
```

配合 vLLM 主仓 `vllm/vllm/v1/core/sched/scheduler.py` 的时序：
- `request_finished`（→ `_set_delayed_free(req, N)`）在 **update_from_output / output 阶段**（vllm L2436-2441）被调用；
- `self.finished_req_ids.add(request_id)` 与 `request_finished` **同一步**完成（L2441）；
- `self.finished_req_ids = set()` 在**下一次 schedule() 末尾**（vllm L1437）清空。

因此任何完成请求 `r` 的生命周期恰好是 **1 个调度间隔**：

```
step N   output:  request_finished(r,3) → _delayed_free_req_ids={r}, stats=(1,3)
                  get_stats() → 上报 (1,3)
step N+1 schedule: build_connector_meta 遍历 finished_req_ids={r} → _set_delayed_free(r,0)
                  → _delayed_free_req_ids={}, stats=(0,0)
                  meta.delayed_free_req_ids = {}   ← 恒空
                  worker get_finished: done_sending = finished_requests ∩ {} = ∅
                  connector_output.finished_sending = ∅
step N+1 output:  update_connector_output → update_finished_sending(∅) → 空操作
                  get_stats() → 上报 (0,0)
```

#### 结论

1. **`meta.delayed_free_req_ids` 恒为空集**。`_delayed_free_req_ids` 标记只有 1 个调度间隔的存活期，无法跨 step 存活到 worker 的异步保存完成时刻；
2. **worker 侧 `done_sending` 恒为 `∅`**。`get_and_clear_finished_requests(meta.delayed_free_req_ids)` 的交集运算恒为空；已完成的请求全部落入 `stale_finished_req_ids = finished_req_ids - ∅` 走 `discard_finished_requests` 被丢弃（见 `kv_transfer.py` L317-339）；
3. **`update_finished_sending` 恒空操作**。PR 在 `update_connector_output` 新增的激活调用（PR diff 的核心改动之一）永远不会收到非空输入，异步保存完成的事件无法回传 scheduler；
4. **Gauge 数值含义失真**。`vllm:ascend_store_delayed_release_requests` 实际输出的是"每 step 新完成请求数"的 1-step 瞬时快照（下 1 step 立即归零），**不是** PR 描述中的 "current requests whose KV blocks remain allocated while asynchronous save completion is pending"。稳态运行时该 Gauge 几乎恒为 0，无法用于观测真实占用。

#### 修复建议（二选一）

- **方案 A（符合 PR 意图）**：在 `build_connector_meta` 中**移除**对 `_delayed_free_req_ids` 的清理（即不再 `_set_delayed_free(finished_req_id, 0)`），让标记在请求完成与异步保存完成之间保持；由 worker 侧 `update_finished_sending` 在真正完成后回收。此时需重新审视 stale 路径对 `finished_requests` 的 discard 是否会误删（见 P2-2），并补充端到端时序测试。
- **方案 B（改语义）**：将 Gauge 改为 Counter（累计完成并延迟释放的请求/块数），或明确文档为"每 step 新增延迟释放请求数"。

### P2-1：测试未覆盖端到端链路，掩盖 P1-1（中）

`tests/ascend_store/test_pool_scheduler.py::test_finished_send_updates_delayed_release_metrics` 的验证方式是**直接调用**两个方法：

```python
scheduler._set_delayed_free("r1", 3)
entered = scheduler.get_stats()          # 断言 (1, 3)
scheduler.update_finished_sending({"r1"})
released = scheduler.get_stats()         # 断言 (0, 0)
```

该测试只证明了"**当 `update_finished_sending` 收到非空输入时**能正确回收"，但没有覆盖真实数据通路：
- 未验证 `build_connector_meta` 在快照前已清空 `_delayed_free_req_ids`；
- 未验证 worker `get_finished` 中 `meta.delayed_free_req_ids` 恒为空导致 `finished_sending` 恒空。

**这正是"单元测试全绿、端到端行为错误"的典型场景。** 建议补充一个集成级测试：构造 `scheduler_output.finished_req_ids` + 同 step `request_finished` 的完整链路，断言 `connector_output.finished_sending` 与指标最终值。

### P2-2：worker `finished_requests` 完成记录残留（泄漏）（中，base 既有）

`kv_transfer.py` `get_and_clear_finished_requests` / `discard_finished_requests` 的竞态窗口：

- 请求 `r` 在 step N 完成；step N+1 `build_connector_meta` 已把标记清空 → `meta.delayed_free_req_ids = {}`；
- step N+1 `get_finished` 中 `stale_finished_req_ids = {r}`；若此刻 `r` 的异步保存尚未完成（`finished_requests` 中无 `r`），`discard` 不生效；
- step N+1 稍后 `r` 保存完成 → `set_finished_request(r)` 将 `r` 写入 `finished_requests`；
- 后续所有 step 的 `finished_req_ids` 均不再含 `r`（vllm L1437 每 step 清空），`r` **永久残留**在 `finished_requests` 中，集合无限增长。

在异步保存耗时 > 1 个调度间隔的常态下，**几乎每个请求都会残留**。该泄漏在 base 分支即已存在（`get_finished` 逻辑未变），PR 未修复它，而其新增的 `update_finished_sending` 因 P1-1 也无力回收这些残留。建议在 `get_finished` 中对"stale"请求同样执行 `discard`，或让完成通知携带时间戳做兜底清理。

### P3 系列：次要问题

- **P3-1** `metrics.py` `AscendStoreKVConnectorStats.aggregate`：`delayed_release_requests` 与 `delayed_release_blocks` 分开判空，若上游 stats 只写入其中一个键（当前不会），`observe` 读取另一键会 KeyError。建议统一用 `self.data.get(...)`。
- **P3-2** `pool_worker.py` `_record_load_get` 直接 `self._kv_stats.record_load_get(...)`，无空检查；而 `kv_transfer.py` L915 同类调用有 `if self._kv_stats:` 保护。实际路径中 `_kv_stats` 始终非空，但两处风格不一致，建议对齐。
- **P3-3** `tests/ascend_store/_mock_deps.py` 的 `_MockKVConnectorPromMetrics.__init__` 用 `list(metric_types.values())` 按**插入顺序**取 gauge/counter/histogram 类；真实生产代码按 `metric_types[Gauge]` 键取。测试 mock 与真实行为解耦，顺序变化时测试会静默错位。

## 四、审查通过项（无问题）

以下改动经核对，确认实现正确、无并发或语义问题：

1. **`_record_load_get` 的计时路径**：`_load_kv`（`pool_worker.py` L2003-2007）与 `_load_kv_tp_mismatch` 的 GET 均被计时，键数取 `len(key_list_c)`（即实际 GET 的键数），与 backend 实际行为一致。
2. **layerwise 排除**：layerwise 模式走 `process_layer_data` 分支，不经过带计时的 `_load_kv`，指标不会混入 layerwise 路径，符合设计意图（layerwise 由 `load_async` 路径承载）。
3. **`start_load_kv` 同步/异步互斥**：`load_async=True` 时 recv 线程执行 GET 并计时；`load_async=False` 时 `start_load_kv` 同步执行并计时。两路径互斥，无双计。
4. **scheduler/worker 两侧 stats 聚合**：worker 侧 `load_get_*` 与 scheduler 侧 `delayed_release_*` 键无碰撞；`aggregate` 合并方向（worker 在前、scheduler 覆盖）正确；`get_stats` 的 take-and-reset 有锁保护（`_kv_stats_lock`）。
5. **Prometheus 暴露**：`vllm:` 前缀与 vLLM 既有命名约定一致；`create_metric_per_engine` + `engine_idx` 路由与 base `KVConnectorPromMetrics` 一致。
6. **`_set_delayed_free` 早退逻辑**：重复入集/出集时提前 return 不更新 stats，在实际调用序列（每请求最多 add 一次、clear 一次）下不产生统计偏差。

## 五、与 PR #15832 的关联

- 本 PR（base `releases/v0.27.1rc`）与 #15832（`feat/ascend-store-transfer-mp`）均深度修改 `ascend_store/pool_scheduler.py`、`pool_worker.py`、`kv_transfer.py`。两者合入 main 时**预计会产生较大冲突**，需协调合入顺序。
- #15832 涉及请求传输通路（本团队正在验证）；#15602 的 delayed_release 指标依赖的正是该通路中"异步保存完成通知"的语义。若 #15832 的延迟释放机制与 vLLM `finished_req_ids` 生命周期交互不同，P1-1 的修复方案需在 #15832 的基础上重新评估。
- 建议：#15602 的指标功能**先合并基础框架（metrics 类 + GET 统计），delayed_release Gauge 待 P1-1 修复后随 #15832 一并验证**。

## 六、总体结论

| 维度 | 评价 |
|---|---|
| 代码质量/风格 | 良好，与 base 风格一致，类型注解完整 |
| 并发安全 | GET 统计与 stats 存取均有锁保护，正确 |
| **功能正确性** | **不达标**——核心指标 `delayed_release_*` 因标记生命周期恒为 1 step 而失效，`update_finished_sending` 恒空操作 |
| 测试质量 | 单元测试充分，但**缺少端到端链路验证**，无法暴露主缺陷 |
| 合入建议 | **有条件合入**：GET 计时部分可合；delayed_release 指标需按"方案 A 或方案 B"修复并补充时序测试后再合 |

**一句话结论**：GET 加载指标实现扎实、可直接采用；但"延迟释放"指标的数据通路存在设计级缺陷（scheduler 侧提前清理 + worker 侧过滤恒空），导致 PR 的核心卖点实际不可用，需修复后合入。
