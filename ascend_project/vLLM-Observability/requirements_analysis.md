## 一、原始需求记录

### 1.1 需求背景（当前性能测试分析的三大问题）

1. **依赖 profiling 进行，依赖性能重测**：只能获取到单点的性能结果，不能获取整体测试周期内的性能表现，性能测试分析效率低。
2. **各个特性的理论和实际优化状态不能实时感知**：比如 EPLB 需要单独离线打点、修改代码才能获取，特性复用效果极难观测。
3. **推理引擎内部的异常状态依赖复现日志**：对于请求异常终止、cache block 分配失败等表现状态，缺少统计呈现。

### 1.2 需求收益

提升推理性能优化、异常分析效率。

### 1.3 硬件产品形态

通用。

### 1.4 需求内容描述

1. vLLM 的性能指标、特性满足度、异常状态等指标支持可度量。
2. 完成监控平台对接 vLLM 指标可视化。

### 1.5 验收标准

| # | 验收项 | 说明 |
|---|--------|------|
| 1 | 新增支持 tokenizer 时间统计 | **已有其他需求跟踪，该需求不做要求** |
| 2 | 新增支持池化 KV Cache 加载耗时指标（请求粒度） | 本需求交付 |
| 3 | 新增 KV Cache 延迟释放状态的请求数量（涉及 PD 分离和池化） | 本需求交付 |

## 二、需求分析

### 2.1 需求定性

这是一个**可观测性（Observability）需求**，核心目的是：把 vLLM-Ascend 推理引擎的内部运行状态做成可度量的指标，并对接监控平台可视化，摆脱"跑 profiling 拿单点数据 + 翻日志复现问题"的低效分析方式。

归类：
- **领域**：易用性（RP3）
- **技术方向**：Metrics 埋点 + Prometheus 指标暴露 + 监控平台对接
- **涉及场景**：PD 分离（Prefill-Decode Disaggregation）、池化（Pooling / KV Cache 池化，如 mooncake/AscendStore）

### 2.2 三大痛点与目标能力映射

| 痛点 | 现状问题 | 目标能力 |
|---|---|---|
| 性能分析靠 profiling | 只能拿单次测试的性能快照，看不到整个测试周期（如 7 天长稳）的性能趋势 | 指标持续采集，形成时间序列，支撑长周期性能表现分析 |
| 特性优化效果不可实时感知 | 比如 EPLB 是否生效、复用效果如何，要改代码、离线打点才能知道 | 特性满足度指标实时暴露，无需改代码打点 |
| 引擎内部异常无统计 | 请求异常终止、cache block 分配失败等只能靠复现日志 | 异常状态指标化（计数/分布），平台看板呈现 |

### 2.3 需求内容解读（两大块）

1. **指标可度量**：在 vLLM/vLLM-Ascend 中新增性能指标、特性满足度指标、异常状态指标的埋点。
2. **平台对接**：指标暴露（通常是 Prometheus `/metrics` 端点），由监控平台采集并出看板。

### 2.4 验收标准逐条解读（真正的交付物）

#### 标准 1：tokenizer 时间统计
明确声明**不在本需求范围**，由其他需求跟踪，**无需在本需求中实现**。

#### 标准 2：池化 KV Cache 加载耗时指标（请求粒度）★核心交付
- **含义**：统计每个请求从 KV 池（如 mooncake/AscendStore）**加载 KV Cache 花了多久**。
- **价值**：这是池化场景"transfer 收益是否兑现"的直接量化证据。
- **度量形态**：请求粒度（per-request），大概率是 Histogram/Summary 分布 + 平均值/P95/P99。

#### 标准 3：KV Cache 延迟释放状态的请求数量 ★核心交付
- **含义**：统计处于"延迟释放"状态（请求已结束但 KV block 未立即回收，留待复用）的请求数。
- **适用场景**：PD 分离和池化。
- **价值**：直接暴露复用窗口内的请求规模，量化 prefix caching/复用链路的实际收益。
- **度量形态**：Gauge（当前处于延迟释放状态的请求数）或 Counter（累计发生过延迟释放的请求数）。

### 2.5 与当前 PD/池化验证工作的关联

本需求与正在进行的 PD/池化专项验证（详见 PD_POOLING_TEST_STRENGTHENING_930.md）高度重合：

1. **标准 2 量化 mooncake KV pool 加载行为**：此前需要重启 vLLM 并开启 DEBUG 日志才能跟踪 mooncake KV pool 的 PutStart、transfer 耗时等行为；有了该指标后，"池化 transfer 是否发生、耗时多少"可以直接在监控看板查看，无需重启加日志。
   - 关联历史结论：vllm 默认 enable-prefix-caching 导致本地 cache 命中，阻碍跨 worker KV transfer；KV pool PutStart 保持为 0 的原因（num_tokens_to_save < chunk_boundary 或请求未完成）。
2. **标准 3 对应 KV block 生命周期管理**：此前验证的 prefix caching 复用、cache_transfer_granularity=4096 过大导致短 prompt 无法 save 等问题，本质都是在调"延迟释放/复用"这条链路；该指标能直接暴露复用窗口内的请求规模。
3. **支撑 9/30 专项的性能基线目标**：专项时间计划中 9/19–9/24 需要完成"性能基线 + 7 天初始稳定性数据"，本需求的指标正是这类长周期度量能否自动化采集的前提；第 10 节"CI 14 天历史数据、失败分类、flaky/SLO 看板"同样依赖指标体系。

### 2.6 与 SR20260820223202（Layerwise 池化性能优化）的配套关系

本需求（AR）是可观测性需求，SR20260820223202 是高性能优化需求，两者是**"度量工具 + 优化本体"** 的配套关系：

- SR 需求的"极光监控大盘"指标（not overlapped 读取时间、延迟释放 req 排队）即本需求的验收标准 2/3 的深化与落地场景
- SR 需求验证"DRAM 池化相比 HBM 基线劣化 ≤5%"是否达标，依赖本需求交付的指标来证明（not overlapped 时间小说明掩盖效果好）
- "监控平台"在本需求中的具体形态即"极光监控大盘"
- 两个需求存在进度耦合：指标埋点若延迟，SR 需求的达标验证缺少直接证据

详细分析见同目录《SR20260820223202_Layerwise池化性能优化需求分析.md》。

## 三、一句话总结

这是一个易用性/RP3 需求，为 vLLM-Ascend 补上"指标埋点 + 监控看板"能力，验收聚焦两个新指标——**池化 KV Cache 加载耗时（请求级）** 和 **KV Cache 延迟释放请求数**，都服务于 PD 分离/池化场景的性能与异常分析。

## 四、附：实施层面的初步思考（供后续参考）

### 4.1 指标暴露技术路径（推测）

- vLLM 上游已有 Prometheus 指标暴露机制（`/metrics` 端点，vllm:distributed_*, vllm:cache_* 等系列指标）。
- 本需求大概率是在 vLLM-Ascend 侧扩展指标定义：
  - KV transfer 相关：`vllm:kv_transfer_load_duration_seconds`（Histogram，请求粒度）
  - 延迟释放相关：`vllm:kv_cache_delayed_release_requests`（Gauge/Counter）
- 监控平台侧完成采集 + 看板配置。

### 4.2 潜在验证关注点

- 指标在池化（mooncake/AscendStore）与 PD 分离两种部署形态下都能正确上报。
- 请求粒度指标的量纲与分布合理性（P50/P95/P99）。
- 延迟释放请求数与 prefix caching 复用行为的一致性（可对照 enable/disable prefix caching 的对照实验验证）。
- 看板可视化呈现与监控平台（VisionIT 生态）的对接验收。

### 4.3 与专项测试计划的衔接

| 专项计划项（930 文档） | 本需求提供的支撑 |
|---|---|
| 8/24–8/27 CI 历史数据导出 | 指标体系是历史数据可持续采集的基础 |
| 9/19–9/24 性能基线、7 天稳定性数据 | KV 加载耗时指标直接进入性能基线度量集 |
| 第 10 节 CI 看板（flaky/SLO） | 异常状态指标（请求异常终止等）可纳入失败自动归因 |
