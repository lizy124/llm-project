# 1. 背景与测试设计

## 1.1 被测对象：PR15832 与 mp 模式

PR15832 在 vllm-ascend 仓库实现了基于 mooncake 传输引擎的 ascend\_store KV pool：推理引擎在 prefill 完成后将 KV cache 分块（chunk）写入 mooncake 集群存储（save），后续相同前缀的请求命中时从存储读回（load），从而跨引擎实例复用 KV、跳过重复 prefill。

该 PR 提供两种传输执行方式：

- **base 路径（use\_multiprocess=False）**：KV 的序列化与 BatchPut 传输在引擎进程内的 worker 线程执行。这是当前主线行为，是本次验证的对照组。
- **mp 路径（use\_multiprocess=True）**：引擎启动时为每个 TP 秩（TP8 即 8 个）fork 一个独立传输子进程，KV 传输卸载到子进程执行，引擎与传输子进程通过 IPC（共享内存队列 + 信号量）交互。设计动研发机是传输不再与 prefill/decode 抢占引擎进程的 CPU 与 HCCL 资源。

**验证目标链**（按提出顺序）：

1. mp 与 base 的 KV 传输性能对比（用户第一优先级：传输本身耗时与带宽，其次端到端）；
2. 09-12 首测 mp 失败后：区分"超时值过小 / 完成事件丢失 / 子进程 hang"三种假设；
3. 死锁是否间歇性、发生频率多少（多轮交替验证）；
4. 存储正确性与落库体量；
5. 能否规模化落地的工程判定。

## 1.3 负载设计（bench\_test.py，与 135 服务器同源、原样使用）

| 参数                                       | 值                                            | 说明                                                                                                        |
| ---------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| BT\_PREFIX\_LEN                          | 32768                                        | 前缀长度 32k token                                                                                            |

| mooncake segment                         | 32G（34359738368 字节）                          | 由 24G 上调——139 实测每秩 KV 需求 27.4G，24G 装不下；local\_buffer 1G；protocol=ascend；master 127.0.0.1:50088；池总上限 256GB |

**KV 容量背景**：该配置下引擎 KV 池容量约 50,747 token，而 19 请求 × 32k ≈ 620k token，请求必然分批排队执行——设计内行为，两模式负载完全相同，不影响对比有效性。

**每轮数据采集点**：bench 打点行（cold done / round wall / hit / hit\_tokens / rps）；mooncake master 每 10s 的 Admin Metrics 行（Mem Storage / Keys / clients 数）；引擎 DEBUG 日志（save/load 事件、put 行、shm\_broadcast 告警）；mp 模式下 8 个子进程的独立日志；每轮运行前后的 /dev/shm 对象数与信号量集数快照。

## 1.4 判定标准（预先约定并写入编排脚本）

- **运行成功（SUCCESS）**：bench 退出码 0 且日志出现 `round=3` 打点且每轮 hit ≥ 8；
- **死锁（DEADLOCK）**（用户指定判据，编排脚本 watcher 以 30s 粒度自动检测）：引擎日志出现 `No available shared memory broadcast block` 告警 + bench 进度计数停滞 + master keys 停滞 + mp 子进程日志 mtime 超 300s，四条同时满足累计 300s；
- **环境失败（EARLY\_FAIL）**：引擎初始化阶段失败（典型为显存不足 ValueError），与死锁严格区分——混为一谈会得出"mp 频繁失败"的错误结论；
- **交替验证方案**（用户指定）：base/mp 交替各 5 轮，每轮完全重来——杀引擎、重启 mooncake master（清空存储池）、重新收集数据。

# 4. 分析与论证

## 4.1 数据正确性：mp 存储的数据语义正确 ✅

**证据**：两天全部 14 个成功轮（base 6 + mp 8）hit 均为 19/19、hit\_tokens 均为 548,861，逐轮逐位一致；请求级 `cached_tokens=32768` 全部命中（结果 json 逐请求比对）。

**论证**：hit 完全一致说明 mp 路径存储的 KV 与 base 语义等价——mp 写入的 92.72GB 中**必然包含全部有效数据**（否则无法 19/19 命中），多余部分是冗余写入而非"多存了别的有效内容"。这把问题从"正确性"收窄为"冗余"（§4.3），也证明 mp 模式功能可用、可作为修复的基础。

## 4.2 性能：多轮数据推翻单样本结论，mp 冷启动与稳态均更慢 ❌

### 4.2.1 上午单样本曾得出相反结论（如实记录结论演变）

09-13 上午仅有 v2/repro 各一次运行：base cold 171.5s vs mp cold 110.1s（mp 快 36%），rps 1.161 vs 1.132（差 2.5%，判等价）。当时结论"稳态不亏、cold 有优势"。下午交替 5v5 + 补跑 + 追加的多轮数据显示该结论不成立。

### 4.2.2 两个批次结论相反的原因（实事求是归因）

1. **上午 base v2 的 171.5s 被污染**：它 10:07:30 启动，距 mp v2 崩溃（10:06:23）仅 1 分钟。mp v2 崩溃泄漏的进程与显存回收（下午的 mp6→mp7 段实测该回收过程约 10 分钟）极可能拖慢了它。下午批次每轮之间有完整的 kill + 等待，base cold 回落到 61.9-95.3s 区间——171.5s 是离群值，不具代表性。
2. **上午"rps 等价"是单样本撞上的**：上午 base 稳态轮 16.2-16.9s，下午 12.4-13.5s（下午系统状态更干净、TBE 编译缓存全热）；上午 mp 稳态轮 16.4-17.2s，下午 16.1-20.2s——**base 变快了而 mp 没变**，上午恰好落在两模式相近的窗口。
3. **下午批次是有效对照**：同一编排脚本、交替执行（排除时段系统漂移）、n=5 vs n=7、hit 逐位一致（负载等价）、每轮环境清理——mp cold 慢 29.3%、稳态 wall 慢 28.3%、rps 低 23.5% 是当前证据强度下的可信结论。

### 4.2.3 mp 为何更慢——机制分析

- **稳态劣化（23-28%）**：mp 模式下每轮 load 命中需经子进程 IPC 往返（8 个常驻子进程，每 TP 秩一次跨进程同步与数据拷贝），base 在引擎进程内直接完成。劣化幅度与 IPC 开销量级自洽。此为机制推演，精确拆分（per-rank save/load 耗时审计）列为遗留项。
- **cold 劣化（29%）**：cold 阶段包含全量首次 save。mp 路径除传输本身外，还需子进程启动、mooncake lazy init（首 put 串行化实测 4-134s，见 §2.5）、以及 8× 冗余数据的实际写盘（92.72GB vs 2.82GB，实际写盘吞吐需求为 base 的 33 倍）。
- **上午"mp cold 有优势"的假象根源**：对比对象 base v2 恰好处在被污染的最差状态。

## 4.3 存储膨胀 32.9×/46.7×：确定性缺陷，机制已半解 ❌

**事实链（全部 master 实测，无一推断）**：

1. 同一逻辑负载（hit\_tokens 548,861 逐位一致）：base 全部 6 轮精确落 2.82GB/4,270 keys；mp 全部 8 轮精确落 92.72GB/199,430 keys；
2. mp 死锁轮的直接证据：空池上 8 个子进程并行 put 同一批逻辑 chunk1 数据**全部成功**，master 收到 5,698 keys ≈ 712 × 8——每个 rank 都把同一批逻辑数据 put 了一遍。**mp 子进程之间无跨 rank 去重**；base 路径由引擎进程内统一的 exists 检查去重，因此只有 1×；
3. 8× 复制只能解释 key 数膨胀的 8 倍，实测 46.7×——**剩余约 5.8×（46.7 / 8）来自其它机制**，候选解释：mp 路径的 key 粒度更细（chunk 子分片）、同 key 多版本写入。精确定位需审计 `mp/client.py` 的 store/exists 分片与 key 生成逻辑（列为主要遗留项，本文记录现象与已实证部分）。

**风险量化**：92.72GB 已占 master 256GB 池上限的 **36.2%**（同负载 base 仅 1.1%）。线性外推，该 master 在 mp 模式下最多支撑当前负载约 2.7 倍即触顶；且膨胀会按 rank 数线性放大（TP16 即 16× 复制起步）。**规模化部署前必须修复，这是比死锁更硬的阻断项——它 100% 复现。**

## 4.4 间歇性死锁：真实存在、低频、机制已定位到回调路径 ⚠️

**完整证据链（mp v2 死锁轮，三份独立日志 + py-spy 交叉验证）**：

```
09:35:54  master 收齐 chunk1 全量（2.65GB / 5,698 keys，PutStart=PutEnd 全闭环）
          —— 传输已 100% 完成 ——
09:36:21  引擎开始报 shm_broadcast 阻塞（每分钟 1 条，持续 30 分钟）
          子进程：8/8 停在 poll() —— put 早已返回，空闲等新命令（py-spy 实抓）
          父 Worker：8/8 停在 clock_nanosleep() —— 轮询等一个永不到的完成信号
10:06:23  1800s 超时耗尽，实例崩溃
```

**判定推理**：数据已全部落库（排除传输层问题）+ 子进程空闲（排除子进程 hang，假设③否定）+ 超时已放大 15 倍仍挂（排除超时配置，假设①对死锁不成立）⇒ 死锁点必然在"子进程 put 完成 → 引擎 save 完成事件"之间的回调/事件路径（`mp/client.py` 内），即假设②。

**频率统计（本验证核心问题）**：

- 干净环境 mp 完整运行 9 次：1 挂 8 成，点估计发生率 **11.1%**；
- 二项分布 Wilson 95% 置信区间：**\[2.0%, 43.5%]**——n=9 不足以收窄，只能确认"非必现、非零概率"；
- 下午连续 7 轮（交替重启、master 反复清池、TBE 冷热混合）零复现；
- 唯一观测到的相关性线索：挂死轮首次 put 串行化 6-134s vs 成功轮 4-54s——mooncake lazy init 的 8 子进程并发竞争越强越可能触发完成事件丢失。此为线索，非结论。

**严格区分（重要）**：mp2/mp7/mp8/mp9 四轮失败是环境连坐（显存不足 ValueError 直接报错，见 §3.4），**不是死锁**。若不加区分，会把 mp 失败率错误地统计为 5/13。

**与 HANDOVER 三假设的对应终局**：①超时过小——成立但仅解释 v1 失败（120s 硬编码，已改可配），非死锁主因；②回调/事件丢失——**成立**（v2 实证）；③子进程 hang——不成立（py-spy 证明空闲）。

## 4.5 资源泄漏：mp 每轮 +8 shm 为确定性缺陷 ❌

**证据**（§3.3 全表）：mp 每轮 /dev/shm 对象恰好 +8，5 轮零例外（71→79→87→95→103→111）；base 7 轮全部零增量。

**机制归因**：8 个 TP 秩各泄漏 1 个传输子进程的 shm 对象（引擎 fork 的子进程退出时 IPC 基础设施未彻底回收），且跨轮不回收、持续累积。长周期反复拉起的服务中该泄漏线性增长（本验证两天从 71 涨到 111+，事故期间一度达 377）。另有每次 mp 退出固定报 248 leaked semaphores + 10 leaked shared\_memory（成功与崩溃退出签名相同），属 vLLM multiproc 基础设施清理缺陷，一并记录。

## 4.6 环境故障链与测试方法论教训（如实记录）

本验证中 **12 轮失败全部来自环境/操作问题而非被测代码**，故障链与教训如下：

**故障链一：异常退出的残留拖垮下一轮。** base2 引擎静默死亡（未归因，疑 NPU 驱动层）→ 残留进程占卡约 10 分钟 → mp2（23.93 GiB）、base3（7.65 GiB）显存连坐连败。教训：编排脚本在启动前必须做显存/进程真实检查（等待回收完成），不能假设 kill 后资源立即释放。

**故障链二：双实例并行 + 清理失效的复合事故。** rogue 编排实例（13:31:51）与正式实例（13:34:07）并行：两者 kill\_engine/restart\_master 互相杀对方进程 → mp7/mp8 显存墙假象 → 失败又泄漏更多进程 → 加上 `kill_engine` 的 pkill 自匹配 bug（`pkill -f "VLLM::"` 先匹配执行它的 wrapper bash 自身，清理命令从未真正执行）+ `wait_npu_free` 的 awk 列解析错误（恒返回"空闲"的假阳性门控）→ 僵尸滚雪球至 **169 个进程**，占卡约 40 分钟，被用户点破后外科清除。教训：①自动化清理必须自证生效（清理后复查计数为 0），不能假设生效；②监控视野必须覆盖全局进程表与显存水位，不能只盯编排进度文件；③编排脚本需要实例锁（lockfile + 启动前查重）；④pkill 模式串必须用 `[x]` 防自匹配。

**方法论正例（保证结论可信的三件事）**：①每轮独立目录 + 独立 master（清池），数据不串轮；②死锁判据预先量化写进脚本（四条件 + 300s 累计），避免事后主观判定；③失败轮逐轮归因（区分死锁/显存连坐/脚本 bug），不把环境失败算到被测代码头上。

# 5. 结论

## 5.1 对 PR15832 mp 模式的最终判定

对"mp（use\_multiprocess=True）在 DSV4-Flash TP8 + mooncake + 32k 前缀 + 32G segment 规模下是否可用"的完整回答：

| 维度       | 判定                          | 依据                                              |
| -------- | --------------------------- | ----------------------------------------------- |
| 功能/数据正确性 | ✅ 可用                        | 14 轮成功 hit 19/19、hit\_tokens 548,861 逐位一致（§4.1） |
| 冷启动性能    | ❌ 慢 29.3%                   | base 81.7s（n=5）vs mp 105.6s（n=7）（§4.2）          |
| 稳态性能     | ❌ 慢 23.5%（rps）/ 28.3%（wall） | 多轮受控对照（§4.2）                                    |
| 存储体量     | ❌ 32.9×/46.7× 膨胀，100% 复现    | 14 轮确定性数据 + 8× 复制实证（§4.3）                       |
| 稳定性      | ⚠️ 间歇性死锁 1/9（CI 2.0%-43.5%） | 完整证据链定位到 client.py 回调路径（§4.4）                   |
| 资源泄漏     | ❌ 每轮 +8 shm 确定性泄漏           | 5 轮零例外（§4.5）                                    |
| **综合**   | **不建议合入/放量**                | 性能无优势 + 确定性膨胀阻断项 + 死锁风险未排除                      |

**关键定性**：mp 模式"能用"（数据正确）但"不划算"（更慢、更占存储、会漏资源）且"不省心"（低概率死锁）。设计动机（传输卸载避免抢占引擎资源）在实测中不仅没有兑现性能收益，反而在两个维度上都劣于进程内路径。

## 5.2 三个遗留假设的终局回答（09-12 晚提出）

| 假设                | 判定                    | 依据                                                            |
| ----------------- | --------------------- | ------------------------------------------------------------- |
| ① 超时值过小（120s 硬编码） | 部分成立——解释 v1 失败，但非死锁主因 | v2 超时放大到 1800s 仍死锁；数据 09:35:54 全落库、10:06 才崩                   |
| ② 传输完成但回调/事件丢失    | **成立**——死锁根因          | master PutStart=PutEnd 闭环 + 子进程 idle（poll）+ 父进程等信号（nanosleep） |
| ③ mp 子进程本身 hang   | 不成立                   | py-spy：8 子进程全部空闲在 poll                                        |

## 5.3 修复建议（按优先级）

1. **跨 rank 去重（最高优先，修膨胀）**：mp 子进程 put 前引入跨 rank 去重——由 rank0 统一做 exists 检查后广播 put 清单，或 master 侧按逻辑 key 去重。同时审计 `mp/client.py` 的 key 生成粒度，解释并消除剩余约 5.8× 的额外膨胀。验收标准：同负载落库 ≤ 2.82GB × 1.1。
2. **回调路径可观测 + 死锁修复**：在 client.py 的"put 完成 → 事件 set"路径逐跳打点（每跳带 rank 与时间戳），复跑触发（当前约 11% 概率，平均 9 轮可复现一次）抓丢点；重点排查 mooncake lazy init 并发竞争（挂死轮首 put 串行化 6-134s 显著长于成功轮 4-54s 的线索）。
3. **稳态劣化归因与优化**：用 DEBUG 日志时间戳差值法拆解 mp 子进程 IPC 开销在每轮 load 路径中的占比，确认 23-28% 劣化是否可优化（如批量 IPC、共享内存直读）；若不可优化则 mp 路径在该负载形态下无性能存在意义。
4. **泄漏修复**：mp 引擎退出时彻底回收 8 个传输子进程的 shm 对象与信号量（每轮 +8 的确定性泄漏，以及退出时 248 sems + 10 shm 的 resource\_tracker 告警）。
5. **修复后复测**：按本报告 §2.6 的交替验证框架复测（建议 base/mp 各 ≥5 轮），验收标准——死锁 0/N（N≥20）、落库 ≤ 3.1GB（base × 1.1）、稳态 rps 差距 ≤ 5%、每轮 shm 增量 = 0。
