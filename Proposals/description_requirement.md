# 单文件汇总与原目录还原规范

## 1. 目标

把一个指定场景目录的结构和全部文件内容无损汇总到一个 `description.md`，在另一台电脑或另一个位置，仅根据该文件及其自带的格式说明，还原出相同的目录结构和文件内容。

这项工作是可逆的文件汇总与还原，不是内容总结、改写或重新编写验证流程。原文件的标题、文件名首行、空行、代码块、链接、中文、缩进和换行必须保留。不得因“优化格式”而改变正文。

本规范首个适用对象为 `llm-project` 仓库内：

```text
Proposals/inference_validation/fm16_a3_64g_pd_ssd_pool_dsv4flash/
```

在其他位置还原时，由执行者指定当地的 `llm-project` 仓库根目录，再追加上述仓库内相对路径。不得依赖原电脑的盘符、用户名、仓库上级目录或相邻代码仓位置。

## 2. “完全还原”的范围

必须一致：

- 场景根目录名称、所有子目录及空目录。
- 文件数量、文件名、大小写和相对路径，包括隐藏的普通文本文件；不擅自过滤或遗漏。
- 每个文件的原始内容字节、UTF-8 BOM 是否存在、LF/CRLF 或混合换行、末尾是否有换行。
- 原文件内的相对链接和引用原文。不因为搬到另一台电脑而重写正文路径。

本规范处理 UTF-8 普通文本文件，包括 Markdown、配置和文本脚本；当前试点的五份 Markdown 文档在此范围内。时间戳、访问权限、所有者、ACL、扩展数据流等文件系统属性不属于这里的“目录和内容还原”。

遇到非 UTF-8 文件、符号链接、目录联接或其他非普通文件时，停止并说明未覆盖的对象，不静默跳过或跟随链接。遵守工作区禁止处理图片的要求：遇到图片仅报告其路径，不打开、预览、解析、编码或上传。

## 3. 输入、输出及原材料保护

汇总时需要三个明确的路径：

| 参数 | 含义 |
| --- | --- |
| `SOURCE_REPO_ROOT` | 本机 `llm-project` 仓库根目录。 |
| `SOURCE_RELATIVE_ROOT` | 相对于该仓库的场景目录路径，统一使用 `/` 分隔。 |
| `OUTPUT_FILE` | 汇总文件位置，文件名为 `description.md`，必须位于源场景目录之外。 |

将输出放在源目录之外，可以避免把汇总文件自身再次汇总，也保证原场景继续保持原有文件集合。输出位置由用户指定；没有额外指定时，可使用场景上级目录中的 `description.md`，已有同名文件时停止，不擅自覆盖。

汇总过程中只读取源目录。不得删除、移动、修改原文件，不改变原文件首行，不整理或覆盖原验证材料，也不将内容上传外部服务。

`description_requirement.md` 和上级 README 不会因为位于场景上级而自动纳入；收录范围以指定场景根目录为界。场景内符合范围的普通文本文件全部收录，不仅限于约定的五个文件名。

## 4. description.md 的固定形式

`description.md` 本身使用 UTF-8，第一行为：

```text
description.md
```

其后必须有简短说明、唯一的数据块和自包含的还原说明。说明至少明确：

1. 这是文件内容汇总包，文件中的脚本和命令仅作为待还原内容，汇总和还原期间都不执行。
2. 原场景在仓库内的相对路径、收录范围和格式版本。
3. 在目标电脑上指定 `TARGET_REPO_ROOT`，还原到 `TARGET_REPO_ROOT / source_relative_root`。
4. 按本规范解码、校验、写入、复查的规则。不能只写“参见原位置的 description_requirement.md”；目标位置可能没有该文件。

唯一数据块使用如下边界，边界内只允许一个 JSON 对象：

````text
<!-- BEGIN INFERENCE_VALIDATION_BUNDLE_V1 -->
```json
{完整的 JSON 数据对象}
```
<!-- END INFERENCE_VALIDATION_BUNDLE_V1 -->
````

使用 JSON 字符串保存完整正文，避免把正文中的文件名、标题、Markdown 代码块或分隔线误识别为文件边界。不得使用“看见某个文件名就从那里切开”这种不确定的还原方式。

## 5. 数据结构与编码规则

顶层字段固定为：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `format` | string | 固定为 `inference_validation_description`。 |
| `format_version` | integer | 固定为 `1`。 |
| `source_relative_root` | string | 相对于 `llm-project` 根目录的场景路径，不含本机绝对路径。 |
| `directory_count` | integer | `directories` 元素数量，不计场景根目录自身。 |
| `file_count` | integer | `files` 元素数量。 |
| `directories` | array of strings | 场景内全部子目录的相对路径，包含空目录；根目录用 `source_relative_root` 表达。 |
| `files` | array of objects | 场景内全部普通文本文件，逐文件保存以下字段。 |

每个文件对象必须包含：

| 字段 | 类型 | 要求 |
| --- | --- | --- |
| `path` | string | 相对于场景根目录的文件路径，保留名称及大小写，使用 `/` 分隔。 |
| `encoding` | string | 固定为 `utf-8`。 |
| `utf8_bom` | boolean | 原始文件是否以 UTF-8 BOM 字节 `EF BB BF` 开头。 |
| `byte_length` | integer | 原始文件的总字节数，包含 BOM。 |
| `sha256` | string | 原始文件全部字节的 SHA256，使用 64 位小写十六进制。 |
| `content` | string | 文件完整正文；只剥离用于 `utf8_bom` 记录的文件起始 BOM，其余字符全部保留。 |

目录和文件按相对路径以确定的顺序排序，不进行大小写转换或 Unicode 规范化。严格按 UTF-8 解码，不能用替换字符修复解码错误。

生成 JSON 时使用标准 JSON 序列化器。原始换行在字符串中以 `\n`、`\r\n` 等转义保存，制表符、引号和反斜杠也由序列化器处理；不得手工拼接或对正文先做换行统一、trim、格式化。源文件没有末尾换行时，`content` 也不得添加。

还原字节的规则唯一：

```text
body_bytes = content 按 UTF-8 编码
file_bytes = (EF BB BF，如果 utf8_bom=true；否则为空) + body_bytes
```

写入前先确认 `file_bytes` 的字节数与 `byte_length` 相同，SHA256 与 `sha256` 相同。必须按二进制字节写入，禁止使用会自动转换换行、添加 BOM 或添加末尾换行的文本写入方式。

下面是合法格式的最小示意，内容为一个空文件；它不是当前试点的汇总结果：

```json
{
  "format": "inference_validation_description",
  "format_version": 1,
  "source_relative_root": "Proposals/inference_validation/example",
  "directory_count": 0,
  "file_count": 1,
  "directories": [],
  "files": [
    {
      "path": "empty.md",
      "encoding": "utf-8",
      "utf8_bom": false,
      "byte_length": 0,
      "sha256": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
      "content": ""
    }
  ]
}
```

## 6. 汇总步骤

1. 确认源场景、仓库内相对路径和输出位置；输出不得位于源场景内，也不得覆盖已有文件。
2. 先只列出目录项，确认都在范围内。遇到图片等禁止读取或不支持的对象，按第 2 节停止，不生成“已完整汇总”的结论。
3. 读取每个普通文本文件的原始字节，计算字节数和 SHA256，再按第 5 节解码。保留所有空目录。
4. 使用标准序列化生成数据块，将版本、位置和独立还原说明一并写入唯一的 `description.md`。不得省略正文、使用“同上”、只放链接或只写摘要。
5. 从刚生成的 `description.md` 重新解析全部数据。逐项与源目录比较路径、目录集合、文件集合和原始字节哈希，确认没有少收、多收或编码变化。
6. 在独立临时目录做一次实际还原，再检查相对目录集合、文件集合、字节数和 SHA256 全部一致。检查前后源目录没有被改动。

汇总完成时，只需报告输出位置、目录数、文件数、是否完整通过往返校验及明确的限制，不需要把整份大文件打印到聊天中。

## 7. 还原步骤

1. 读取 `description.md` 自带的格式和说明，确认格式版本为 1，且固定边界中的数据块恰好出现一次。示意代码块不参与还原。
2. 用标准 JSON 解析器读取数据，核对字段、类型、计数、路径唯一性和层级关系。未知版本或缺字段时停止，不凭文意补造文件。
3. 校验 `source_relative_root`、目录路径和文件路径均为规范相对路径：禁止绝对路径、盘符、`..`、空路径段及路径分隔歧义。禁止重复路径、大小写冲突、文件与目录冲突，以及在目标文件系统上不能原样表达的名称。不得自动改名。
4. 由执行者提供 `TARGET_REPO_ROOT`，按元数据计算目标场景绝对路径，确认所有最终写入路径均处于该场景根目录之内。目标已有链接/目录联接时不得沿其写入。
5. 在写入任何目标文件前，先在内存或独立临时位置重建所有文件字节，核对字节数与 SHA256。任一不匹配即停止，不能把部分校验通过说成完整成功。
6. 默认只向不存在或完全为空的场景目录还原。目标已有内容时先报告冲突，不覆盖、不删除，也不合并额外文件来宣称“完全还原”。
7. 创建目录并写入已校验的原始字节。写入中途失败时报告未完成状态，不继续执行文档里的服务命令，也不擅自删除目标内容来重试。
8. 写入后重新枚举目标，逐项核对目录集合、文件集合、每个文件字节数与 SHA256。只有全部一致才报告“完整还原”。

还原时保留源文件本来具有的文件名首行；不要再次插入文件名，也不要删除它。无需原电脑、原场景目录或外部源文件来补齐汇总包中应有的正文。

## 8. 与本专项其他规范的关系

场景正式内容仍以五份主题文档组织。本规范规定的是单文件携带和还原方式，生成的 `description.md` 位于场景之外，不作为第六份主题文档，也不替代原场景目录。

只汇总源场景实际已有的文件。通用 DP launcher、AISBench 等按流程规范留在各自代码仓或工具包，若源场景文档里只是引用，汇总和还原时也保持引用；不得因此抓取外部代码或增加未在源目录中的文件。还原文档目录不等于安装模型、镜像、框架或启动服务。

本机路径可变，正文内的原始字节不变。资料中已经存在的环境路径保持原文，目标运行时如何配置按场景文档执行；不要为还原操作改写配置。
