## 1. 方案与思路

### 1.1 S4 的看护职责

S4 是全家族里唯一的 **MTP3 投机解码 × 池化** 交互载体：

- 模型 = DeepSeek-V4-Flash-W8A8 + `deepseek_mtp`（**num_speculative_tokens = 3**）
- 并行 = 单机 **TP8**（DP1）
- 池化 = memcache + `kv_both` + **`use_layerwise=false`**

看护目标有两类：

1. **接受率（精度侧）**：MTP3 的投机接受率是否被池化变量扰动 → baseline `0.925`，tolerance `0.05`
2. **吞吐（性能侧）**：perf baseline `90`，threshold `0.97`（首跑回填）
   - 两项都要在 **open / close 两个 case** 上各看一遍，共 4 组数字。

### 1.2 为什么是 open / close 两个 case

yaml 里两个 case 共用同一份 `_server_cmd`（含池化），只在 `server_cmd_extra` 的 `--additional-config` 上分叉：

| case | `enable_block_verify` | `enable_entropy_verify` | `enable_cpu_binding` |
|---|---|---|---|
| `deepseekv4-flash-w8a8-enable-open` | `true` | `true` | `"true"` |
| `deepseekv4-flash-w8a8-enable-close` | `false` | `false` | `"false"` |

对照意义：**验证池化叠加后，投机解码的两种拒采样配置都能正常起服与解码**，接受长度量级一致、无异常。

### 1.3 池化叠加方式（与 S3 的关键差异）

- S4 用 **anchor 复用**：`_kv_pool` + `_server_cmd` 定义一次，两个 case 同时挂 → 池化对两 case 同时生效。
- `use_layerwise=false`：S4 的 perf 负载（`GSM8K-in3500-bs2800`）**无共享前缀**，池只承担 **lookup 查询路径**，命中回读路径本就不该触发。
- 因此 S4 里 `kvpool hit tokens` **恒 0 是正常预期**（与 S3 的哨兵语义相反）。真正的哑失效监控在 S3 上。

### 1.4 与 S3 共用同一台机

S4 与 S3 都在 139 上，**共用 memcache 5000/6000 端口**，因此两者**不能同时跑**，必须串行；每次起服前先清残留并做端口预检。

## 8. 性能看护方案修订（2026-10-04，讨论稿）

> 本节是拟合入方案，优先于前文基于 `use_layerwise=false`、独立前缀负载和“命中恒为 0”的历史设计与实测记录；前文保留用于追溯方案演进。

### 8.1 方案结论

S4 从“池服务开启条件下的 MTP3 兼容性冒烟”升级为 **MTP3 × memcache × layerwise 的暖池读写、接受率和性能哨兵**。两个现有 case 均保持原服务数量、模型、TP8、MTP3 和 verify open/close 配置，只把池化变量统一改为真实可读写的形态：

1. `use_layerwise=false` 改为 `use_layerwise=true`，使 DeepSeek-V4 主模型层和 MTP/spec-decode 层进入逐层保存与加载生命周期；
2. 增加 `--no-enable-prefix-caching`，避免本地 HBM prefix cache 抢占命中；
3. 每个 case 内先用 1 条 prefix90 请求写池，再用 64 条同源请求测量从第一条开始的热池读取；
4. runner 在 benchmarks 前记录 speculative metrics 基线、执行完 warmup/perf 后检查 acceptance rate，因此原有 acceptance 门禁会自然覆盖真实池读流量，无需修改 runner。

S4 与 S3 复用相同的 memcache/layerwise 基础路径，但职责不同：S3 看护 DP4×TP4、MTP1 下的基础池读和 GPQA；S4 看护 TP8、MTP3、MTP 物理层以及 block/entropy verify open/close 两种配置下的池读写交互。两者共同失败指向公共池路径，仅 S4 失败则优先定位 MTP3/TP8/verify 组合。

### 8.2 最小配置改动

两个 case 继续共享 `_server_cmd` 和 `_benchmarks_perf` anchor，保证池化配置是 open/close 对比中的常量：

```yaml
_server_cmd: &server_cmd
  - "--no-enable-prefix-caching"
  # 其余原服务参数保持不变
  - "--speculative-config"
  - '{"num_speculative_tokens": 3, "method": "deepseek_mtp", "enforce_eager": true}'
  - "--kv-transfer-config"
  - '{"kv_connector": "AscendStoreConnector", "kv_role": "kv_both", "kv_connector_extra_config": {"backend": "memcache", "lookup_rpc_port": "0", "use_layerwise": true}}'

_benchmarks_perf: &benchmarks_perf
  pool_warmup:
    case_type: performance
    dataset_path: vllm-ascend/GSM8K_prefix90_in65536_bs1000_qwen
    request_conf: vllm_api_stream_chat
    dataset_conf: gsm8k/gsm8k_gen_0_shot_cot_str_perf
    num_prompts: 1
    max_out_len: 1
    batch_size: 1
    request_rate: 0
    baseline: 0
    threshold: 0.97

  perf:
    case_type: performance
    dataset_path: vllm-ascend/GSM8K_prefix90_in65536_bs1000_qwen
    request_conf: vllm_api_stream_chat
    dataset_conf: gsm8k/gsm8k_gen_0_shot_cot_str_perf
    num_prompts: 64
    max_out_len: 1024
    batch_size: 16
    request_rate: 0
    baseline: 1
    threshold: 0.1
```

`pool_warmup` 的 `baseline: 0` 只要求任务成功。正式 `perf` 的 `baseline: 1`、`threshold: 0.1` 是首跑记录占位，不能作为最终性能门禁。

两个 case 会分别启动各自原有的服务和池，因此执行序列分别为：

```text
open 服务/池  → open warmup 写池  → open perf 读池  → open acceptance 判定
close 服务/池 → close warmup 写池 → close perf 读池 → close acceptance 判定
```

池不会跨 case 复用，不能依赖 open 的 warmup 给 close 暖池。

### 8.3 数据集与指标语义

沿用 S3 已核对的数据集结论：`GSM8K_prefix90_in65536_bs1000_qwen` 共 1000 条样本，全部共享同一个全局长前缀；当前本地副本 SHA256 为 `E22FD30B06B8D2A8B98B1A15F06D999E09DFD3E491E12D84E3310E9FBAE7344D`。因此它适合“单热点前缀写入一次，后续并发请求读取”的场景。

S4 的两个门禁含义如下：

| 门禁 | 看护含义 | 不代表什么 |
|---|---|---|
| Output Token Throughput | MTP3 在 layerwise 热池读取下的端到端性能下限 | 不能单独证明每条请求实际命中，首跑仍须查日志 |
| acceptance rate | 池中 KV 被加载后，MTP3 draft/verify 的接受行为是否稳定 | 不是答案正确率，不能替代 AIME/GPQA |

原负载 `GSM8K-in3500-bs2800` 的性能基线 `90` **作废且不得复用**：输入长度、请求规模、并发和冷热语义均已改变。`acceptance_rate: 0.925 ± 0.05` 暂时保留为行为预期，因为 MTP 算法和模型未变；首轮有效运行必须复核其在新长前缀热池负载下是否仍稳定，若系统性漂移则单独重新标定，不能用放宽 perf threshold 掩盖。

### 8.4 基线采样前的有效性门槛

open 和 close 必须分别满足以下条件，运行结果才能纳入基线：

1. 使用最终 YAML 的 TP8、MTP3、`use_layerwise=true`、prefix cache 关闭和 10GB memcache 配置；缩卡、改 TP、缩短输入的结果不纳入。
2. 本 case 的 warmup 请求成功，首次查询允许 miss，并能从日志确认发生 layerwise 写池；至少出现可等价证明保存发生的 PutStart/Keys/逐层保存证据。
3. 本 case 的正式 perf 稳定出现 `kvpool hit tokens > 0` 且 `need to load > 0`。目标是 64/64 请求均有正命中；若日志不是逐请求输出，先确定等价计数口径。
4. 首个有效运行标定 DeepSeek-V4 tokenizer 下的实际 prompt token 数、共享前缀 token 数和命中档位，后续运行必须保持同一档位。
5. acceptance rate 在 open、close 两个 case 中均完成判定；同时记录各自的实际值，不能只记录整体 PASS/FAIL。
6. MetaService、worker、engine 无 OOM、load/save failure 或异常退出，case 结束后 5000/6000 端口正常释放。
7. 排除共享机清场、抢卡、端口冲突和明显硬件异常。存在外部干扰的运行作废并记录原因。

任一 case 没有正命中，即使吞吐和 acceptance 均显示 PASS，也视为场景未成立，不能用于回填基线。

### 8.5 新基线与 threshold 的确定方法

1. 在相同 CI runner、硬件池、镜像、代码提交和最终 YAML 上至少完成 **5 次有效的完整 nightly**；波动接近门限时扩展到 10 次。
2. open、close 分别记录 Output Token Throughput 和 acceptance rate，同时记录 warmup 写池、perf 命中数、hit/load token 档位及外部干扰。
3. 当前两个 case 共用同一份 perf baseline。只有当两者分布接近时，才以两组有效数据合并后的保守中位水平确定共享 baseline；若 open/close 性能存在稳定差异，应解除 benchmark anchor 的基线共享，为两个现有 case 分别设置 baseline，不能用较低共享值掩盖其中一侧回退。
4. threshold 依据有效运行波动决定：全部结果稳定在基准的 97% 以上时采用 `0.97`；正常噪声确实超过 3% 时先定位原因，确认不可消除后再评审 `0.95`；超过 5% 不继续放宽。
5. 回填正式 baseline/threshold 后再完整运行一次，确认两个 case 均通过、均命中池且 acceptance rate 正常。

### 8.6 尚缺的确认项

1. **命中仍是间接门禁**：runner 不解析池日志。当前约束下只能依赖热池吞吐下降间接暴露失效，仍存在假绿风险；首跑和基线阶段必须人工核对 hit/load 证据。
2. **MTP 层实际保存与加载**：代码和单测覆盖 MTP/spec-decode 物理层生命周期，但正式 TP8 模型须从日志确认主模型层与 MTP 层均参与 layerwise 传输，不能只看到普通层写入就判定完成。
3. **10GB 容量**：单个 65k 共享前缀在 TP8、包含 MTP 层时是否稳定驻留须实测。若发生淘汰，优先核对实际 KV 大小和保存范围，再决定调整容量或负载，不能直接用混合命中结果定基线。
4. **warmup 完成语义**：确认 `max_out_len=1` 返回时写池已经完成，正式 perf 第一条即可命中；否则增加最小必要输出长度或等待机制，但不改变正式 perf 负载。
5. **acceptance 统计灵敏度**：runner 会把 warmup 和 perf 期间的 speculative counters 一并统计。warmup 输出仅 1 token，理论上正式 perf 占主导，首跑仍须确认采样量和指标稳定性。
6. **数据集可用性**：S4 使用 a3-800i-8 runner，须确认该 runner 的 pod 缓存中存在 prefix90 数据集；不能只依据 S3 的 a3-800i-16 缓存情况推断。
7. **真实读池答案精度仍缺失**：acceptance rate 不是答案判分。整体答案精度继续由 S1/S2/S3 的 AIME/GPQA 承担；严格的池命中后答案精度仍依赖后续共享前缀可判分数据。
