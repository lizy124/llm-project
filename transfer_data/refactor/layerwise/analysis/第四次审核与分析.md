## 二、v4 自身的新问题（本轮发现）

### 问题 1.【中】"scheduler 侧依赖面"是虚假前提——v4 的本轮新发现不成立

v4 §1.1 末段："本轮新发现（三轮亦未展开）：scheduler 侧 hit check 同样依赖该语义——pool_scheduler.py:348 `key_infos = self.store_scheduler.batch_get_key_info(all_keys)`。若 scheduler 侧 store 亦处 lazy 未初始化态，hit check 拿空 → 全 miss……"，并据此追加 UT 第 6 条。

**这个前提是空集**。memcache_backend.py:100-105：

```python
@classmethod
def create_scheduler_client(cls, parallel_config: ParallelConfig):
    # The scheduler is a single metadata client. It is initialized before
    # the world group exists and must not initialize memcache storage, so
    # keep the old device_id=0/init_bm=False behavior here.
    return cls(parallel_rank, local_rank=0, init_bm=False)
```

（注：引用为语义示意，实际首参为 parallel_config。）`lazy_init` 未传入 → 构造器默认 `False`（memcache_backend.py:47）→ `self._lazy_init = False and _is_device_sdma()` 恒为 False → **构造器内即刻 eager 初始化**（:58-60）。scheduler 侧的 `batch_get_key_info`（:142-151）的 lazy 短路分支永远不会触发——注释本身即写明 scheduler 是"single metadata client"。

v4 的"若 scheduler 侧 store 亦处 lazy 态"是不可能的条件。第 6 条 UT 是对一个不存在的状态做覆盖（无害但无意义）。

有讽刺性的是：v4 本轮证伪了三轮的 assert 细节，自己却引入了一个前提为空的"新发现"——交叉审核的证伪权与出错权并存。

**修正**：
- §1.1 该段删除或改为"scheduler 侧经 `create_scheduler_client` 恒为 eager 构造（lazy_init 默认 False），不受本问题影响"
- §2.2 第 6 条 UT 可删；GVAHitChecker 的常规 UT 自然覆盖 :348 路径

### 问题 2.【微】"PD 分离场景 P 节点即此形态"疑似 D/P 颠倒

纯 consumer（无新块可 save、`new_keys` 恒空）在 PD 分离中对应 **D 节点**（decode 消费方，只 load）；P 节点（prefill 生产方）对每条新请求必然产生可 save 的新块，`new_keys` 非空 → `batch_alloc` 会被调用 → store 会被自愈初始化。疑为笔误。不影响"纯 consumer 形态存在"的论点本身（D 节点即实证）。

### 问题 3.【微】行号漂移

传导链行号有 ±1~10 漂移：`:1394` → 实际 `:1397`、`:1417` ✓、`:1476` → 实际 `:1466`、`:1500` → 实际 `:1502`、`:1608` → 实际 `:1609`。结构断言全部正确，属誊抄精度，不影响结论。
