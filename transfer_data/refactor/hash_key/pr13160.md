# PR 13160: AscendStore KV Pool Refactor

Commit: `b92671404`  
Title: `[Refactor] Simplify AscendStore KV pool Implementation and Unit Tests`

## 结论

这个 PR 主要是一次 AscendStore KV pool 的结构性重构，不是功能新增。核心目标是收敛重复逻辑、简化 scheduler/worker 状态处理、减少对象构造和特殊分支，并同步精简单测。

## 主要改动

- 统一 key、token chunk、block hash、cache family、KV cache group 的处理逻辑，集中到 `config_data.py` 的公共 helper 和 `ChunkedTokenDatabase` 中。
- 减少 `PoolKey` 对象构造，新增直接生成字符串 key 的路径，降低 save/load 批量处理时的分配成本。
- 简化 `KVPoolScheduler`：把新请求、preempt 恢复、running cached request、async load 拆成独立路径，`build_connector_meta()` 只负责调度串联。
- 简化 `KVPoolWorker` 初始化：拆分 `_init_*` 初始化步骤，注册 KV cache 后直接注册 backend buffer 并启动 transfer thread。
- 优化 layerwise 传输：`LayerBatchBuilder` 预计算共享 block 数据，复用 numpy buffer，并对 `(block_id, gva)` 去重，减少每层重复构造。
- 收敛 backend API：删除 `batch_is_exist()`、`MemcacheBackend.init_store()` 等冗余入口；`YuanrongBackend` 批处理统一走分片循环。
- 大幅精简 ascend_store 单测，减少对内部实现细节的耦合，保留关键行为覆盖。

- `tests/ut/distributed/ascend_store/` 下相关单测

## 需要重点关注的风险

- layerwise save/load 路径是否保持原行为。
- hybrid KV cache、DSV4 compress、mamba align 场景下的 block size / cache family / mask 逻辑是否一致。
- TP mismatch 场景是否被正确限制或兼容。
- 后端 lazy init、buffer register、exists/get/put 的调用时序是否仍然满足 memcache/yuanrong 要求。

## 审查结论与证据边界

本轮审查只能支撑一个较窄结论：目前没有发现明确由 `b92671404` 这个 refactor 新引入的编译错误、残留符号引用或被删接口调用断点；但不能据此证明该 PR 没有行为回归。

已直接验证的证据包括：

- 对 `b92671404^..b92671404` 的 15 个变更文件做了 diff/stat 复核。
- 对 `vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store` 和相关单测执行了 `python -m compileall -q`，语法层面通过。
- 搜索 refactor 删除/收缩的符号：`unfinished_request_ids`、`LayerMultiBlockReqMeta`、`target_token_len`、`kv_cache_families_by_group`、`block_keys`、`sizes_per_chunk`、`last_block_key`，未发现外部残留引用。
- 搜索删除的抽象接口：`Backend.batch_is_exist()`、`MemcacheBackend.init_store()`，未发现项目代码仍调用被删除的 `init_store()` 或抽象层 `batch_is_exist()`；当前命中的是后端内部调用底层 store 的 `store.batch_is_exist()`。
- 对两个明显风险点做了父 commit 对比，确认它们不是本 refactor 新增：
  - TP mismatch 专用 save/load 逻辑依赖线程里的 `worker`，但真实线程创建未传 `worker=self`。
  - `MemcacheBackend` lazy init 只由 `put()` 触发，`batch_alloc`、`batch_get_key_info`、`batch_add_lease` 在 store 未初始化时仍会直接 assert。

当前分支仍需关注的既有风险：

- TP mismatch 专用逻辑存在，但发送/接收线程创建未传 `worker=self`，专用路径基本不会走到。
- Memcache lazy init 对 GVA batch API 覆盖不足；纯 consumer load 或 GVA layerwise 首次 load 场景可能在 store 未初始化时触发 assert/失败。

测试覆盖缺口：

- shared GVA data 只测了 `LayerBatchBuilder`，没有测试 `_build_shared_save_data()` / `_build_shared_load_data()` 将 shared data 正确挂到所有 layer task。
- `save_keys` / `load_keys` 通过 shared data 传递后，没有测试 `batch_write_finish` / `batch_remove_lease` 是否按预期调用。
- direct key string prefix cache 没有测试 `set_group_buffers(... group_cache_families=...)` 后 cache family 变更是否清掉旧 prefix。
- `cache_transfer_granularity` 只测 helper，没有测试真实 hybrid/compress scheduler/worker 集成。
- memcache lazy init 基本没有测试，现有测试直接设置 `_lazy_init=False`、`_store_initialized=True` 绕过关键状态。

建议合入前优先补充 shared GVA lifecycle、memcache lazy init、hybrid/compress transfer granularity 的集成单测。
