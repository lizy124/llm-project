  审核发现

  1. 高：kv-28 的上游协议范围没有闭合

  llm-project/draft/issues_10/TOP3.md:130 只点名 KVConnectorOutput 和 scheduler，但新增 failure outcome 还必须覆盖：

  - 两条 worker output 采集路径。

  - code/vllm/vllm/distributed/kv_transfer/kv_connector/utils.py:53 的多 TP/worker 聚合。
  - Ascend 的 code/vllm-ascend/vllm_ascend/core/recompute_scheduler.py:996。
  - PP output 透传判断 code/vllm-ascend/vllm_ascend/worker/worker.py:686。

  尤其是 aggregator 不能简单 union failed IDs：某个 rank 先报告失败时，应暂存 failure，等所有预期 worker 都完成 finished_recving 后，
  在同一个聚合输出中同时发布 completion 和 failure。否则会提前失败请求，或者为了等待 completion 而丢失先到的 failure。

  2. 高：kv-25 的 startup 修复缺少事务性回滚和并发边界

  llm-project/draft/issues_10/TOP3.md:66 只要求 ready 超时与异常传播，但 worker 是按顺序启动多个线程的，见 code/vllm-ascend/
  vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/pool_worker.py:456。

  还应明确：

  - 后启动线程失败时，先前已经启动的 sibling thread 如何停止。
  - ready 超时后，set_device() 若迟到成功，线程不得继续进入消费循环。
  - add_request() 与 fatal 转换必须线性化：任务只能“被接受并最终完成/取消”或“被拒绝”，不能落入两者之间。
  - 当前 counter 注册和入队是两步操作，见 code/vllm-ascend/vllm_ascend/distributed/kv_transfer/kv_pool/ascend_store/
    pool_worker.py:1767，fatal 发生在两步之间会遗留 counter。

  3. 高：sync fail-fast 的“安全终止”条件不足

  llm-project/draft/issues_10/TOP3.md:128 要求在 forward 前安全终止，但上游 start_load_kv() 位于 context manager 的 try/finally 之
  前，见 code/vllm/vllm/v1/worker/kv_connector_model_runner_mixin.py:95。

  直接抛异常会跳过 wait_for_save()、get_finished() 和 clear_connector_metadata()。任务必须二选一并验收：

  - 明确这是 worker/engine fatal，验证进程退出且不会复用残留状态。
  - 支持恢复，则必须保证 connector finalization、metadata 清理和下一 step 可继续执行。

  否则“抛异常”并不等于“安全终止当前 step”。

  4. 中高：GVA rollback 的范围与验收互相矛盾

  llm-project/draft/issues_10/TOP3.md:133 允许 rollback 失败进入 UNKNOWN，但 llm-project/draft/issues_10/TOP3.md:145 又无条件要求
  lease 均无遗留。

  外部 backend 的 batch_remove_lease() 失败时无法保证零遗留。应改为：

  - rollback 成功时验证无遗留。
  - rollback 失败时保留原始 load error，记录 cleanup error，并将 lease outcome 标为 UNKNOWN。
  - 幂等性指本地 cleanup 状态机 exactly-once 调用，除非 backend 明确保证重复 remove 幂等。
