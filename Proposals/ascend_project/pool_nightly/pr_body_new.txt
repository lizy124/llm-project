## Motivation

KV pooling (AscendStoreConnector, both `memcache` and `mooncake` backends, with/without `use_layerwise`) currently has **no nightly coverage**: a pooling regression would not be caught until a manual weekly/CI run happens. This PR brings KV pooling into the DeepSeek-V4-Flash nightly guardrails by **overlapping pooling config onto 4 existing nightly services** -- no new yaml files, no new test cases, no CI/runner script changes. Accuracy + performance are both guarded.

The same integration shape is already proven by two merged weekly cases: `DSv4-Flash-Memcache-PD-layerwise` (multi-node PD, memcache) and `Qwen3.5-397B-Memcache-perf` (single-node, memcache). This PR reuses their structures verbatim.

Ports follow the nightly conventions (memcache 5000/6000, mooncake master 50088 / metrics 50089); memcache pool services are per-case lifecycle on single-node runners and node-0 managed on the multi-node runner.

`kv_load_failure_policy` is deliberately left at the default `fail` (loud failure) everywhere -- silent recompute would mask exactly the read-path bugs this guardrail exists to catch.

**S3 provides the only read-path coverage in the family**: its perf load carries a ~90% shared prefix, so waves 2+ of the batched load hit the pool and load KV back (in S1/S2/S4 the workloads have no shared prefix -- the query path is exercised, the hit path is not). The dataset is already used on the same runner pool by `qwen_3_6_27b_w8a8_A3`, so it is known to be present in the pod cache; it is qwen-tokenizer calibrated, which drifts under the `deepseek_v4` tokenizer -- acceptable for a perf-only sentinel.
