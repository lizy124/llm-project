## 二、发现的问题（按严重度）

### 1.【重要】PR3 × #12854 冲突面被低估

P0 方案 §4 协调表以"本方案不动 kv_transfer.py"为由称 PR3 与 #12854"冲突面小"——**这个推理不成立**。#12854 的自述明确包含 "Moving layerwise GVA resolution and transfer preparation into a dedicated preparer"、"Managing read leases by request with explicit reference counting"，重做的正是 PR3 要迁移的 `_alloc_gvas_for_save` / `_prepare_load_gvas` 同一区域。且两方案存在**设计竞争**：#12854 的 `LayerwiseTransferPreparer` 与 PR3 的 `GVASession` 是对同一职责的两种封装。"PR3 合入后成为 #12854 的稳定基座"是单方面期望，不是协调事实。

**修正建议**：PR3 与 PR5 同等对待——启动前必须确认 #12854 走向（它当前与 main 有冲突，状态未定）。PR1/PR2 不受影响，可立即开工。

### 2.【中】"平移式迁移"名不副实

方案实际引入 ≥5 个新类型：`GVAKeyFactory` / `GVASession` / `GVAHitChecker` / `GVALayerwiseCapable` / `GVALayerwiseThreadContext` + 2 个工厂函数。这是**重新封装**，不是平移。设计本身可辩护（可测性、单一职责、与 ctx 挂接风格一致），但：
- PR 描述不应声称"纯移动无语义变化"，reviewer 需按重新封装的标准做行为等价审查
- 备选最小方案（方法直接挂 MemcacheBackend）会让该类膨胀 ~350 行，方案的选择合理，但应有意识地确认这个取舍

### 3.【小】P0 §2.3 表格事实错误

mooncake_backend.py / yuanrong_backend.py 中**不存在**"5 个 NotImplementedError 存根"——存根只在 base.py。表格声称"各删约 -15 行"是虚构的。设计结论不受影响（接口移入 `GVALayerwiseCapable` 后两后端自然失去这些方法），但执行时 diff 会与方案描述不符。

### 4.【小】PR4 × #14697 协调缺口

P1/P2 的 `on_worker_ready` 方案依赖 `init_store` 末尾 `_register_buffers_if_needed` 补注册语义做等价性论证，而 #14697 明确计划**删除 `init_store`**（构造器内处理）。协调表只覆盖了 PR5×#14697，PR4 需要同样跟进，否则等价性论证的前提可能消失。

### 5.【微】精度瑕疵

- P0-1 标题"重复定义 4 处"夸大：实际 2 处定义 + 1 处 layout 判断 + 1 处 connector 引用（表格内已诚实标注）
- P1/P2 §0 注 3 引用失实：需求分析 §2.1 记的是 ~1620 非 1484（1484 恰是 kv_transfer.py 的非空行计数）；实质结论（>1601 物理行）正确
- 需求分析 §2.2 初版 put/get 表述错误——已在文档内自我修正，属实，但说明第一轮分析有错，第二遍才对（消费文档时注意此类自我修正是否完整）
- ascend_store_connector.py 不解析 backend 字段（P0 方案 §1.3 ④ 的修复代码需自行解析 extra_config，与 pool_worker 同式，方案代码已正确处理）

### 6.【微】PR6 部分内容超出需求 4 范围

`check_all_layers_exists` 迁 metadata.py——文档自己已裁定它**非** backend 相关（key-mode 三后端通用）。这属于需求 3 范畴的收尾，不是需求 4 必需项。规模小可做，但建议在 PR 中明确标注为顺带清理，避免范围蔓延质疑。docstring 的 "MemCache" 中性化（attention_fence.py:31/:65、layerwise_cache_layout.py:71 已核实存在）在范围内，可做。
