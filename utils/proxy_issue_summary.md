# 外网连接排查总结：Clash Verge 与 SakuraCat

- 日期：2026-08-27
- 范围：本机 Windows（Clash Verge + SakuraCat 双客户端）无法访问外网的问题排查与解决
- 结论一句话：**Clash Verge 无法上网的根因是机场（SakuraCat）服务端线路失效；本地 Clash 配置本身健康。最终改用 SakuraCat 客户端在手机热网上成功上网。**

---

## 1. 问题背景与初始症状

- 用户反馈"Clash Verge 连不上外网"，Clash Verge 界面反复提示订阅更新失败。
- 用户明确诉求：**不使用 Clash Verge，直接用 SakuraCat 客户端**配置并上网。

## 2. 诊断过程与证据链

### 2.1 Clash Verge 本地状态核查（结论：Clash 本身健康）
- 进程正常：`clash-verge` + `verge-mihomo v1.19.3` 运行正常。
- 代理端口 `7897` 正常监听，系统代理正确指向它。
- mihomo API（`127.0.0.1:9097`）响应正常，规则匹配正常工作。

### 2.2 机场服务端问题（结论：机场线路已失效）
- **订阅接口返回空**：订阅 URL 返回 HTTP 200 但响应体为空，导致 Clash Verge 报 `profile does not contain proxies`。
- **主域名 DNS 失效**：配置中大量节点使用的 `catcat321.com` 域名在多个 DNS（阿里 / Google）下均解析不出 A 记录。
- **残余隧道失效**：少数 `tube-cat.com` 节点 TCP 端口能连通（握手成功），但 trojan 隧道建立全部超时（延迟测试 503/504）。

### 2.3 SakuraCat 客户端无法启动的根因
- SakuraCat 客户端硬编码连接官方控制面服务器 `sakuracat.com`（地址固化在程序 `app.so` 中）。
- `sakuracat.com` 存在 **DNS 污染**：本地 DNS 返回假 IP `93.46.8.90`（意大利家宽地址），阿里 DoH 返回 `59.24.3.174`（韩国），腾讯 DoH 返回 `8.7.198.46`（韩国）。
- 假 IP 与实际服务器 IP 在 TCP 443 均不可达 → 客户端卡在"无法连接到服务器"。
- 形成"先有鸡后有蛋"困境：客户端要连控制面才能加载节点，连控制面又需要可用的出境通道。

### 2.4 订阅源被 CDN 地区限制
- 订阅域名 `0b96e976-...-com` 的 IPv6 因解析异常导致不可用，用 hosts 强制走 IPv4 后可连通。
- 但订阅内容托管在 **Bunny CDN**，对大陆直连返回 **403 阻止页**，导致无法直接拉取节点列表。

## 3. 关键转折点

- **切换到手机热点（4G/5G）**：热点出口 IP 不在 Bunny CDN 封禁名单内，订阅得以完整下载，并验证了节点真实可用。
- **登录 SakuraCat**：在手机热网环境下 SakuraCat 成功登录并可选节点，最终**能正常访问 Google / YouTube**，问题解决。

## 4. 过程中尝试过并被否定的方案（备查）

- **通过 Clash Verge GUI 导入订阅链接**：报错 `error sending request for url`——原因是 Clash Verge 下载订阅会走自身的失效旧节点代理，请求被打回。
- **向 Clash Verge 运行内核热加载新订阅（PUT /configs）**：代理隧道可建立（CONNECT 200），但实际出站 000 失败。对照实验（另起独立 mihomo 于 7898 端口加载同一配置 → 全部 204 成功）证明：**节点本身可用，问题出在绕过 Clash Verge 自管机制热加载导致的状态不一致**。
- 结论：不应绕过客户端自身的配置管理机制直接篡改运行内核。

## 5. 验证方式（可直接复用）

```text
# 通过某代理端口验证境外连通性
curl.exe -x http://127.0.0.1:<代理端口> https://www.google.com/generate_204
# 期望：HTTP 204
```

## 6. 恢复与清理（已在用户确认后完成）

- Clash Verge 运行内核已重新加载回自身配置（103 个节点，与原先一致）；未改动任何 Clash Verge 持久配置文件。
- 临时创建的全部测试脚本、订阅文件与独立测试内核目录（`nvm2`）已删除。
- 临时测试出的独立 mihomo 进程已停止。

## 7. 遗留事项（需用户知悉，未擅自处理）

- **系统 hosts** 中仍保留一条将订阅域名强制走 IPv4 的记录；对当前 SakuraCat 上网无影响。如需彻底还原 hosts，可手动移除。

## 8. 经验与要点

1. **判断"是客户端问题还是服务端问题"时，用"独立实例 + 同配置"做对照实验最有效**（本次通过另起 mihomo 定位出节点好用、是热加载方式的问题）。
2. **DNS 污染特征**：同一域名在不同解析源给出差异极大的 IP，且本地解析的 IP 反向查多为无关家宽地址。
3. **"客户端能否上网"不能等同于"机场可用"**：SakuraCat 需要先连通被墙的控制面，故在无可用通道时会形成死锁。
4. **CDN 地区封禁**：订阅托管在 Bunny CDN 时，大陆 IP 常被 403，切换非封禁网络（如手机热点）可绕过。
5. **避免绕过客户端自身的配置机制**：直接热加载运行内核会破坏状态一致性，应通过客户端的 profile / GUI 机制落地。
