## 1. 方案与思路

### 1.1 为什么选 S3 做读路径哨兵

四个载体里只有 S3 的负载带 ~90% 共享前缀（`GSM8K_prefix90_in65536_bs1000_qwen`），批量发压第二波起会命中池并回读 KV。S1/S2#1/S4 的负载无共享前缀，只走 lookup 查询路径、**从不走命中回读路径**。所以读路径覆盖全部压在 S3 身上。

### 1.2 两处关键设计

1. **`--enable-prefix-caching` → `--no-enable-prefix-caching`**
   关掉本地 prefix cache 后，**池成为唯一 KV 命中路径**。若命中数仍为 0，说明池确实没被读，而不是被本地 cache 抢了——这是哨兵语义成立的前提。

2. **`--kv-transfer-config`：AscendStoreConnector / `kv_both` / `layerwise=true`**
   `layerwise=true` 才会启用写池分支（`_start_layerwise_put_keys` / `_prepare_layerwise_put_session` / `save_kv_layer`）；`layerwise=false` 的 `get_num_new_matched_tokens` 只做查询，不构成写路径看护（此结论在 S2#1 回退档①上被实测确认：`PutStart=0 / Keys=0`）。

### 1.3 合并前硬门槛：R9 gate

**风险**：prefix-caching 关闭后，上游（vLLM v0.30.0 配对）是否仍为请求生成 `block_hashes` **无法静态核实**，而池 lookup 直接消费它。若不生成，失败形态是**哑失效**——池从未被读、考题照常全绿。

**对策**：设 R9 gate 为合并前硬门槛。必须在 a3 上拿到「prefix-off 下命中 > 0」的正向信号，PASS 才允许合并、才允许触发 S3 的 nightly。

### 1.4 并行度依据（DP4×TP4 为什么能跑）

- 模型 `/mnt/weight/DeepSeek-V4-Flash-w8a8-mtp` 约 **280GB**（全 int8 专家权重）。
- `DP4×TP4 = 16 卡` 且开了 `--enable-expert-parallel` 时，专家权重按 **DP×TP 全局切分** → EP=16 → 280GB/16 ≈ **17.5GB/卡**，可塞进 64GB HBM。
- 早期「DP4×TP4 在 64GB/卡 OOM」的结论是**错的**：那是 R9 gate 用 **DP1 偏离形态**（EP=4 → ~70GB/卡）导致的误判。原样形态实测 **OOM=0**，已推翻。

### 1.5 数据集决议（后续替换）

S3 Phase 2a 的 perf 负载后续由我们自行造数并替换。当前 yaml 中的 `GSM8K_prefix90_in65536_bs1000_qwen` 仅是现阶段配置，**不是必须沿用的数据集**；验收重点是新负载能让后续请求**确实命中池并回读 KV**。

- 按 S3 实际请求模板和 DeepSeek-V4 tokenizer 核对共享前缀的逐 token 一致性与长度，确保达到实测的 16384 token 命中粒度；不能只依据数据集名称或原始文本长度判断。
- 用新负载在 S3 原样形态下发起先冷后热的请求，确认后续请求的服务日志出现 `kvpool hit tokens > 0` 且 `need to load > 0`，请求正常完成；若命中始终为 0，则不算覆盖池化读路径。
- 更换负载后重新实测并回填 perf 基线与阈值，不沿用旧负载的性能数值。Phase 2b 若使用 perf 暖池供精度用例判卷，还需保证两门用例渲染出的共享前缀逐 token 一致。

- 发压：串行两条共享前缀请求，前缀 `PREFIX_CHARS=120000`（≈30k token，> 16384 粒度门）
- 判据：请求 #2 日志 `kvpool hit tokens: N` 且 `N > 0`

**判据行（原样）**：

```
[pool_scheduler.py:715] Reqid: cmpl-adf28a408f789d1c-0-ab111cbd,
Total tokens 22949, kvpool hit tokens: 16384, need to load: 16384
```

**结论**：`--no-enable-prefix-caching` 下请求**仍携带 `block_hashes`**，memcache 池被**真实消费**（请求 #1 冷池无命中、请求 #2 命中 16384 token 并 load；两条响应均正确 43/82）。→ proposal §6 R9 担心的「哑失效」**被实测推翻**；**`e37e47e33` 无需 revert**。

> **脚本自身两处缺陷（P0，待修）**：
> 1. `PREFIX_CHARS` 默认 `17000`（≈4.2k token）**低于本模型粒度门 16384** → 结构上不可能命中；
> 2. 判据 `N_LINES < 2 → FAIL` 会把 PASS 误判为 FAIL（`kvpool hit tokens` 仅在命中 > 0 时打印，冷池请求本就不打行）。
>
> 修法：`PREFIX_CHARS` 提到 ≥ 200000（≈32k token）；判据改为「存在 `kvpool hit tokens: N` 且 `N > 0`」，去掉「行数 ≥ 2」前提。

### 阶段 3：读路径实测（本次待重跑）

这一步是为补完「原样形态（DP4×TP4）下的正向命中证据」，替换阶段 1 的 DP1 偏离版记录。

> DP4 原样形态下命中归因说明：池是全局共享的，req#2 无论落到哪个 DP rank，命中都代表真实的池读回读；若落在与 req#1 不同的 rank 上，反而是**跨 engine 池共享**的更强证据。

## 8. 性能看护方案修订（2026-10-04，讨论稿）

### 8.1 方案结论

S3 的池化性能看护收敛为**单热点长前缀的暖池读取性能**：先用 1 条请求把公共前缀写入池，再用原有规模的 64 条请求测量读池后的端到端吞吐。保持原 S3 perf 的 `num_prompts=64`、`batch_size=16`、`max_out_len=1024`、`request_rate=0` 不变，只在正式 perf 前增加 1 条 warmup。

本地实查 `GSM8K_prefix90_in65536_bs1000_qwen/test.jsonl`：

| 项 | 结果 |
|---|---|
| 样本数 | 1000 |
| 单条 `question` 字符长度 | 270558～272007，中位数 271233.5 |
| 全部样本逐字符相同的公共前缀 | 231129 字符（字符口径约 85.2%；`prefix90` 是构造时的 token 口径） |
| 数据结构 | 1000 条共享**同一个全局前缀**，不是 64 组不同前缀的一一配对数据 |
| 本地文件 SHA256 | `E22FD30B06B8D2A8B98B1A15F06D999E09DFD3E491E12D84E3310E9FBAE7344D` |

因此该数据集适合看护“一个热点前缀写池后，后续并发请求读池”的场景；不覆盖“64 个不同前缀分别写入、再由 64 条请求逐一命中”的多 key 场景，后者若需要须另行造配对数据。

### 8.2 最小配置改动

服务侧保持当前 S3 池化配置：

- `kv_pool.type=memcache`，meta/config-store 端口 5000/6000；
- `AscendStoreConnector`，`kv_role=kv_both`，`backend=memcache`，`use_layerwise=true`；
- `--no-enable-prefix-caching`，避免本地 HBM prefix cache 抢占命中，使正式 perf 的跳算收益可归因于池读取。

benchmark 顺序暂定为 `acc-gpqa → pool_warmup → perf`，其中 `perf` 保留原 S3 的 64 条/并发 16 规模：

```yaml
    benchmarks:
      acc-gpqa:
        # 原配置保持不变

      pool_warmup:
        case_type: performance
        dataset_path: vllm-ascend/GSM8K_prefix90_in65536_bs1000_qwen
        request_conf: vllm_api_stream_chat
        dataset_conf: gsm8k/gsm8k_gen_0_shot_cot_str_perf
        num_prompts: 1
        max_out_len: 1
        batch_size: 1
        request_rate: 0
        baseline: 0       # 项目现有 warmup 惯例：仅要求任务成功，不设吞吐下限
        threshold: 0.97

      perf:
        case_type: performance
        dataset_path: vllm-ascend/GSM8K_prefix90_in65536_bs1000_qwen
        request_conf: vllm_api_stream_chat
        dataset_conf: gsm8k/gsm8k_gen_0_shot_cot_str_perf
        num_prompts: 64
        max_out_len: 1024
        batch_size: 16
        request_rate: 0
        baseline: 1       # 仅首跑记录占位，不能作为正式门禁
        threshold: 0.1    # 基线重复测量后回填
```

`pool_warmup` 按项目现有长前缀 warmup 惯例设为 `baseline: 0`、`threshold: 0.97`，实际判定下限为 0，只要求任务成功。单机 runner 按 YAML 顺序串行执行 benchmarks，且同一 test case 内服务和池不重启；warmup 返回后，正式 perf 才开始。R9 已用串行两请求实测过“请求 1 写池、请求 2 命中并加载 16384 token”，因此该阶段划分在机制上已有依据。

原非池化 prefix0 基线 `181.8813` **作废且不得复用**：负载已变为 prefix90，服务已开启池化，正式 perf 又是暖池读取，指标语义完全不同。

### 8.3 基线采样前的有效性门槛

只有同时满足下列条件的一次运行，才能纳入新基线样本：

1. 使用最终拟合入的完整服务参数、池配置、模型/代码版本和数据集版本；临时缩卡、改 DP/TP、改输入长度的结果不纳入。
2. `pool_warmup` 请求成功，首次查询允许 `kvpool hit tokens=0`，并能从日志确认发生 layerwise 写池。
3. 正式 `perf` 阶段必须稳定出现 `kvpool hit tokens > 0` 且 `need to load > 0`。目标是 64/64 请求均有正命中；若日志按批次聚合或并非逐请求打印，须先确定等价的计数口径。
4. 首个有效运行先标定该数据集在 DeepSeek-V4 tokenizer 下的实际 prompt token 数、公共前缀 token 数和稳定命中档位；不能只凭数据集名中的 `prefix90`/`65536` 判断。后续运行命中档位应保持一致。
5. MetaService、worker、engine 全程无异常退出、OOM、load failure；case 结束后池服务和端口正常释放。
6. 排除共享机 `pkill`、其他作业抢卡、端口占用、明显硬件降频等外部干扰。存在明确外部干扰的运行作废并记录原因，不允许静默删掉正常但偏低的数据。

若正式 perf 没有正命中，即使吞吐任务显示 PASS，也判为无效运行，不能用于回填基线。

### 8.4 新基线与 threshold 的确定方法

1. 在相同 CI runner、硬件池、镜像、代码提交和最终 YAML 上至少完成 **5 次有效的完整 nightly**；若波动接近门限或离散明显，扩展到 10 次。
2. 每次记录 Output Token Throughput、运行时长、warmup 写池证据、perf 命中请求数、`kvpool hit tokens`/`need to load` 分布、池错误与机器异常。
3. 新 `baseline` 取有效运行 Output Token Throughput 的**中位数**，避免单次快跑或慢跑主导基线。
4. `threshold` 不预先拍死：
   - 若全部有效运行均不低于中位数的 97%，且没有明显双峰，采用 `0.97`；
   - 若正常环境波动超过 3% 但不超过 5%，先定位来源；确认是不可消除的稳定噪声后，再评审是否采用 `0.95`；
   - 若有效运行低于中位数 5% 以上，不继续放宽门限，应先解决场景、调度或环境不稳定问题。
5. 回填 `baseline`/`threshold` 后再跑 1 次完整 nightly，确认新门禁能够通过且池命中证据仍成立，方可视为性能看护就绪。

### 8.5 尚缺的确认项

1. **命中门禁如何自动化**：现有 runner 只按 Output Token Throughput 判性能，不会解析 `kvpool hit tokens`。若坚持 runner 零改动，命中只能作为日志巡检规则，存在长期 nightly 假绿风险；需决定接受间接吞吐门禁，还是后续增加轻量日志断言。
2. **GPQA 对池容量的影响**：暂定顺序保留线上语义为 `acc-gpqa → warmup → perf`，但 GPQA 在 `layerwise=true` 下也会写入无关 KV。首跑须确认 10GB 池容量下不会挤掉刚写入的热点前缀；若发生容量/淘汰干扰，再评审调整顺序或容量，不能直接用被污染的数据定基线。
3. **warmup 完成即写池完成**：R9 串行请求已经正向验证，但仍需在 DP4×TP4 原样形态和正式数据集上确认 perf 的第一条请求即可命中；否则要增加明确等待/写池完成判据。
4. **指标灵敏度**：runner 当前只门禁 Output Token Throughput。池读取回退更可能首先反映在 TTFT/prefill latency；首跑需同时观察相关指标，判断 OTT 是否足够敏感。若不敏感，单靠现有 runner 无法形成可靠的读池性能门禁。
5. **数据集固定性**：正式基线应绑定数据集 revision 或文件校验值，防止 ModelScope 同名数据更新后基线失去可比性；上表 SHA256 是当前本地副本，CI 缓存版本仍需核对。
6. **warmup 参数实跑确认**：确认 `max_out_len=1` 能完整触发 layerwise 写池且 aisbench 正常产出结果；若不满足，改为最小可稳定完成的输出长度，但不得改变正式 perf 的原有 1024 输出长度。
