# LLM 推理问题集与答案文档整理规范

本文记录后续整理 LLM 推理问题时的统一规范。目标是把问题、答案、源码证据、性能取舍和排查方法拆分清楚，形成可长期维护、可复盘、可检索的学习资料。

参考文档：`llm_inference_question_driven_learning_path.md`

重点要求：回答每个问题时，必须优先参考 `llm-project/research_workspace/documents/question` 中已经梳理好的文档，并结合 vLLM 代码仓源码证据，例如 `D:/lzy/project/kv_pool/code/vllm`。

目录要求：答案集合统一放在 `llm-project/research_workspace/documents/overview/answer_set`，问题集合统一放在 `D:/lzy/project/kv_pool/llm-project/research_workspace/documents/overview/question_set`，后续问题和答案全部按规范整理到这两个文件夹里。

---

## 1. 总体组织方式

后续不把所有问题和答案混在一个长文档里，而是采用两层结构：

1. **问题集文档**：集中列出问题，按模块、优先级或学习阶段归类。
2. **答案文档**：每个问题对应一个独立、完整、可单独阅读的答案文档。

问题集文档中的每个问题都必须能直接链接到对应答案文档。

推荐目录结构：

```text
research_workspace/documents/overview/
  llm_inference_question_set.md          # 问题集索引
  answers/                               # 每个问题的详细答案
    001-vllm-core-positioning.md
    002-vllm-request-lifecycle.md
    003-enginecore-step-flow.md
```

如果某个模块问题很多，可以继续按模块拆分：

```text
answers/
  engine/
  engine_core/
  scheduler/
  kv_cache/
  attention/
  parallelism/
  quantization/
  cuda_graph/
  operators/
```

## 2. 问题集文档规范

问题集文档只负责做索引和进度管理，不写长答案。

每个问题建议包含：

```text
- [ ] Q001：vLLM 的核心定位是什么？它主要解决 LLM serving 中哪些问题？
  - 模块：vLLM 总览
  - 优先级：P0
  - 答案：[001-vllm-core-positioning.md](answers/001-vllm-core-positioning.md)
  - 来源：llm_inference_question_driven_learning_path.md:303
```

字段含义：

- `Q编号`：稳定编号，后续不要因为排序变化频繁修改。
- `问题`：必须是一个可以被完整回答的技术问题。
- `模块`：问题所属模块，例如 Engine、EngineCore、KV Cache、Attention。
- `优先级`：沿用 P0 / P1 / P2。
- `答案`：链接到独立答案文档。
- `来源`：记录问题来自哪个文档、哪一行或哪个材料目录。
- `状态`：用 checkbox 表示是否已经完成初版答案。

问题集文档不承担源码细节、性能分析和排查流程，这些必须放到答案文档里。

## 3. 答案文档必须达到的深度

每个答案不能只写一句定义，必须按 L1 到 L4 递进。

### L1：概念边界

必须回答：

- 它是什么？
- 它解决什么问题？
- 它不负责什么？
- 它和相邻模块的边界是什么？

合格标准：能用 3 到 5 句话说明职责边界，不混淆相邻模块。

### L2：端到端链路

必须回答：

- 输入是什么？
- 输出是什么？
- 中间经过哪些对象？
- 哪个对象负责状态变化？
- 哪个对象负责真实计算？

合格标准：能画出链路图，并能解释每个箭头为什么存在。

### L3：源码对象

必须回答：

- 相关类 / 函数在哪里？
- 哪些字段承载关键状态？
- 哪些方法改变状态？
- 哪些配置会改变执行路径？
- 哪些对象是计划，哪些对象是结果？

合格标准：能用源码路径定位关键对象，能说明调用关系。

### L4：取舍、性能与排查

必须回答：

- 这个设计为什么这样做？
- 它优化了什么指标？
- 它牺牲了什么？
- 什么情况下收益不明显？
- 出问题时如何排查？
- 如何设计 benchmark 验证？

合格标准：能结合 TTFT、TPOT、吞吐、显存、通信、kernel launch、正确性风险分析问题。

## 5. 写答案时的硬性要求

1. **每个问题一个独立答案文档**，不要把多个大问题塞进一个答案里。
2. **问题集只做索引**，不要在问题集里写长答案。
3. **每个答案都必须有源码证据**，源码引用格式统一为 `path:line`。
4. **每个答案都必须区分负责和不负责**，避免模块边界混淆。
5. **每个答案都必须写主链路**，最好用文本图或 Mermaid 图表达对象流转。
6. **每个答案都必须区分计划对象、状态对象、结果对象**。
7. **每个答案都必须写性能或正确性取舍**，不能只停留在概念解释。
8. **每个答案都必须写排查路径**，说明出问题时从哪些对象、字段、日志或指标开始看。
9. **不确定的点不要假装确定**，统一放到“我还不确定的点”。
10. **初版可以短，但结构必须完整**；后续通过源码证据、图和 benchmark 逐步补全。

---

## 6. 推荐工作流

1. 从 `llm_inference_question_driven_learning_path.md` 中选一组问题。
2. 把问题录入 `llm_inference_question_set.md`，分配稳定编号。
3. 为每个问题创建一个答案文档。
4. 先写 L1 和 L2，确保边界和主链路清楚。
5. 再读源码补 L3，必须记录 `path:line`。
6. 最后补 L4，把性能、正确性、排查和 benchmark 写完整。
7. 回到问题集文档，把已完成的问题勾选。

---

## 7. 完成度分级

为了便于持续推进，每个答案可以标注完成度：

- `草稿`：只有初步理解，结构已建好，但源码证据不足。
- `可复述`：L1 / L2 清楚，能讲清边界和主链路。
- `可定位`：L3 完整，能用源码路径定位关键对象和调用关系。
- `可排查`：L4 完整，能结合指标、源码和 benchmark 分析问题。
- `可复盘`：有图、有源码证据、有实验或真实排查案例。

目标不是一次写完，而是让每个问题都能从“草稿”逐步升级到“可复盘”。
