区分 Memcache/GVA layerwise 与非 GVA key-based layerwise，见 `pool_worker.py:145-155` 和 `pool_scheduler.py:169-171`。非 Memcache 配置没有在入口被拒绝，且 `pool_worker.py:460` 之后确实会创建 key-based layerwise 收发线程。这只能证明 Mooncake/YuanRong 的 layerwise 路径可进入，不能证明其已获得支持承诺、测试覆盖和硬件验证。

与此同时，公开文档还有以下相互冲突或过时的描述：

- `kv_pool.md:41` 称 layerwise 仅支持 Prefill node；`layerwise_kv_pool.md:9-10,75,123-179` 又明确给出 `kv_both`、`kv_producer` 和 `kv_consumer` 场景。
- `layerwise_kv_pool.md:237-239` 称多 KV cache group/hybrid 会直接抛 `NotImplementedError`；但 `pool_worker.py:377-394` 已遍历多 group，`test_layerwise_cache_layout.py:387` 也覆盖 multi-group SFA descriptor。当前真实限制更细：启用 buffer reuse 时，`layerwise_cache_layout.py:255-267` 拒绝非 `AttentionSpec`，不能把这一限制等同于“所有 hybrid/multi-group 均不支持”。
- `layerwise_kv_pool.md:229-241` 笼统称 CP 未集成；但 `dsa_cp.py:1308,1383,1550-1551` 已调用 layerwise wait/save、KV-written 和 attention gate hook，`attention_cp.py:566-569` 也已记录 gate。存在 hook 仍不等于端到端支持，因此文档既不能继续笼统否定，也不能未经测试改成笼统支持。
- TP mismatch 已在 `pool_worker.py:224-235` 对 layerwise 明确拒绝，支持矩阵应保留这一限制。

因此，任务 3 的验收对象必须至少包含 backend、KV role、attention backend、CP、hybrid/multi-group、MTP/sparse/non-`AttentionSpec` 和 TP mismatch。每个组合只能标为“支持”或“不支持”；未验证组合按不支持处理，并在配置阶段尽早拒绝。

### 2. 高：任务 3 同时存在两个确定的默认值错误和一个可导致无限等待的校验缺口

- Memcache/GVA 路径在 `layerwise_cache_layout.py:128-134` 的默认预取层数是 `min(layerwise_num_shared_buffers, 8)`；非 GVA key-based 路径在 `pool_worker.py:427-428` 的默认值是 `1`。文档将所有路径统一写成 `1`，不准确。
- `layerwise_kv_pool.md:88` 称 layerwise 的 `discard_partial_chunks` 默认值为 `false`；`pool_scheduler.py:135-142` 对普通和 layerwise 分支实际都使用 `True`。该重复分支本身也表明代码没有第二套默认值。
- GVA 路径会拒绝 `layerwise_prefetch_layers < 1`，非 GVA 分支只调用 `int()`。配置为 `0` 时，`pool_worker.py:1693-1699` 首轮不会提交任何 layer，随后 `pool_worker.py:1709-1715` 仍可能等待当前层完成事件，形成无退出条件的等待。负数有同样问题；`bool` 和非整数输入在两条路径上的接受行为也不一致。

原稿只要求“默认值对齐”不足以封闭问题。最终任务必须固定两条路径的默认值，统一解析规则，并通过构造期校验保证非法值不可能进入运行线程。

### 3. 高：任务 6 的阻塞和 server 线程退出风险成立，但“lookup 异常”的范围必须准确

`LookupKeyClient.lookup()` 在 `pool_scheduler.py:1185-1187` 直接执行 `send_multipart()` 和阻塞 `recv()`，没有 deadline、`SNDTIMEO`、`RCVTIMEO` 或 Poller；scheduler 在 `pool_scheduler.py:568-575` 也没有 RPC 异常边界。因此 worker 无响应时 scheduler 可无限阻塞。

`LookupKeyServer` 在 `ascend_store_connector.py:312-333` 对帧数量、固定宽度整数、msgpack 内容、参数范围和发送失败均无请求级异常处理。解析异常会结束 daemon thread，后续请求不再被处理。

但 backend `exists()` 等异常通常不会直接杀死该 server：`pool_worker.py:2352-2420` 已捕获异常并返回 `0`。现状的问题是 backend 故障被折叠成正常 cache miss，协议和指标无法区分二者。最终任务应分别处理：

- 报文/参数错误：返回明确的协议错误且 server 循环继续；
- backend/lookup 错误：返回明确的服务端错误，由 client 执行统一 fail-open；
- transport/timeout/REQ 状态错误：client 关闭旧 socket、重建连接，并对当前请求 fail-open。

### 4. 高：任务 6 原稿给出了两个互斥的降级结果，无法严格验收

原稿允许“继续重算，或向上层返回可恢复错误”。当前 scheduler 接口只消费整数命中长度；`pool_scheduler.py:577-578` 已清晰表明 `0` 命中返回 `(0, False)`，即不创建外部 KV load，继续本地计算。最小且与现有语义一致的唯一契约应为：

> lookup RPC 任一失败均 fail-open 为 `0` 个外部命中；当前请求不重试、不加载外部 KV，由 scheduler 继续本地重算；失败 socket 必须在返回前关闭并重建，使下一次请求可恢复。

不能把异常直接抛给 scheduler 作为默认行为。若未来需要 fail-closed，必须作为独立显式配置和独立任务设计，不能混入本任务验收。

### 5. 中：任务 6 还缺少协议、deadline 和生命周期边界

当前成功响应只是裸字节整数，client 未校验响应长度、命中值范围或是否超过 `token_len`；server 也未校验请求固定字段是否恰为 4 字节、group id 是否为非负整数、hash 列表是否为允许类型。最终任务应定义版本化成功/错误响应，并保证 REP 收到请求后恰好回复一次，否则 REP socket 本身会进入不可继续收包的状态。

超时必须覆盖单次 lookup 的完整 wall-clock，而不是分别给 send 和 recv 各一份超时。`close()` 目前只关闭 socket（`pool_scheduler.py:1190-1191`、`ascend_store_connector.py:338-339`），没有终止 context、停止 server loop 或等待线程退出；最终验收应包含 client/server 重复关闭、server 线程退出和 context 释放。

### 6. 中：任务 8 证明了结构性队头阻塞条件，但没有证明性能收益

所有 transfer thread 使用单个 `queue.Queue`（`kv_transfer.py:333`），并在一个线程内按 FIFO 逐个执行 `_handle_request()`（`kv_transfer.py:496-518`）。key-based load 在 `kv_transfer.py:1245-1252` 依次等待 save owner 和 attention gate；GVA load 在 `kv_transfer.py:1553-1561,1589-1591` 依次等待 save CPU event、save NPU event 和 attention gate。队头依赖未满足时，后续任务无法被检查，结构性 head-of-line blocking 成立。

但是 gate 的 `wait()` 在 `attention_fence.py:53-61` 同时包含 CPU condition wait 与 `torch.npu.Event.synchronize()`；把它们合并成一个 `gate wait` 指标无法判断等待发生在 host 还是 NPU 时间线。GVA save-owner wait 也必须拆成 CPU event 与 NPU event 两段。只有观测到“后续任务已满足全部依赖，却被未就绪队头阻塞”，才能证明 ready queue 或按 gate 分组有调度机会。

此外，`layerwise_num_shared_buffers` 决定共享 KV buffer 布局，`layerwise_prefetch_layers` 在 `pool_worker.py:1693` 只决定首次提交深度。提高 prefetch 不必然增加已分配的 NPU KV buffer 数；需要测量的是 in-flight task/metadata、lease、backend 队列和实际峰值内存，不能继续用“更多临时 buffer”作未经测量的统一结论。

## 最终审查意见

- 任务 3：保留 P1，但必须重写为“支持矩阵 + 配置契约 + 默认值/非法值修复”，不能只改文档。

## 任务 6：[Correctness] 为 ZMQ lookup RPC 增加有界 deadline、错误协议与连接恢复

> 建议优先级：P0

### 背景

非 layerwise 模式下，scheduler 通过 ZMQ REQ/REP 向 worker 查询外部 KV 命中。当前 client 在发送后无界阻塞等待回复；server 的收包循环没有请求级异常边界，畸形帧或解码异常可终止 server thread。backend lookup 异常虽被 worker 捕获并折叠为 `0`，但协议无法区分真实 miss 与服务端故障。REQ/REP 在超时或未完成收发状态后也不能安全复用现有 socket。

相关位置：

- `pool_scheduler.py:568-578,1156-1192`
- `ascend_store_connector.py:293-340`
- `pool_worker.py:2339-2420`
- `tests/ut/distributed/ascend_store/test_pool_scheduler.py:569-610`

### 固定行为契约

- 新增 `lookup_rpc_timeout_ms`：单位毫秒，默认 `5000`，只接受正整数；`0` 或负数不表示无限等待，必须在初始化阶段拒绝。
- timeout 是单次 `lookup()` 从开始发送、等待回复到完成响应校验的完整 wall-clock deadline；实现不能让 send 和 recv 分别消耗一份完整 timeout。
- 任一 timeout、transport、REQ 状态、协议、解码或 server lookup 错误，当前请求均 **fail-open 为 `0` 个外部命中**，scheduler 返回无外部命中并继续本地重算；默认行为不得向 scheduler 抛出异常，也不得在同一次调用中无界重试。
- client 在失败时先以 `linger=0` 关闭旧 REQ socket，再创建新 socket；失败调用返回前必须完成恢复，使下一次正常 lookup 可以成功。
- server 对每个已收到的请求恰好发送一次成功或错误响应。单请求异常不得结束服务循环；若 REP socket 自身进入不可恢复状态，server 必须关闭并重建 socket。

### 任务

1. 为 client 实现上述完整 deadline、初始化校验、fail-open 和 socket 重建。
2. 保留当前请求字段语义，但严格校验帧数量和类型：两个整数帧必须恰为 4 字节，`token_len`/`hbm_hit_tokens`/group id/hash 列表必须满足类型、非负性和范围约束。
3. 将响应改为单帧、版本化 msgpack envelope：
   - 成功：`{"version": 1, "status": "ok", "hit_tokens": N}`；
   - 失败：`{"version": 1, "status": "error", "code": CODE, "message": SANITIZED_MESSAGE}`。
   client 必须校验版本、字段集合、类型及 `0 <= hit_tokens <= token_len`。不支持的版本按协议错误 fail-open。该 RPC 连接同一实例内的 scheduler/worker，双方同时升级；不要求旧裸 4 字节响应兼容，但必须在设计说明中写明协议切换。
4. 调整 worker/server 边界，使真实 miss 与 backend/lookup 异常在 RPC 层可区分；client 对后者仍按统一契约降级为 `0`。
5. 增加按失败类别聚合的限流 warning 和计数指标。日志仅记录错误码、阶段、耗时、token/hash/group 数量，不得记录完整 hash、key 列表或原始报文。
6. 完成 client/server 生命周期：`close()` 可重复调用；停止 server loop，保证后台线程在有界时间内退出，关闭 socket 并释放 ZMQ context；关闭过程中不得产生未捕获异常。

### 验收标准

- server 不存在、无响应或回复过晚时，`lookup()` 在 `lookup_rpc_timeout_ms` 加明确测试容差内返回 `0`，不存在无限阻塞。
- timeout、`zmq.Again`、`EFSM`/REQ 状态错误、断连、空响应、旧 4 字节响应、错误版本、缺字段、错误类型、越界/负数命中均 fail-open，并重建 socket。
- server 对缺帧、多帧、非 4 字节整数、非法 msgpack、非法 group/hash/token 参数和 backend 异常返回版本化错误；处理后 thread 仍存活，下一次合法请求成功。
- scheduler 级回归测试证明 RPC 失败返回 `(0, False)`、不创建外部 load spec，并继续本地计算路径。
- 正常的零命中、部分命中、完整命中和多 KV group 语义无回归；成功响应仍严格限制在 `token_len` 内。
- client/server 连续调用两次 `close()` 均安全，server thread 和 ZMQ context 无泄漏。
- 提供正常路径改动前后延迟对比；错误日志和测试输出不包含完整 hash payload。

### 交付件

- PR、deadline/协议/fail-open/socket 状态机设计说明和兼容性说明。
- client、server、scheduler 层异常与恢复单测。
- 正常路径开销数据、日志/指标示例和回退方案。

## 任务 8：[Perf/Investigation] 量化 layerwise recv 队头阻塞并评估依赖感知调度

> 建议优先级：P3

### 背景

layerwise recv thread 使用单 FIFO 队列串行处理任务。队头任务可能等待共享 buffer 的 save owner 或 attention boundary；等待期间后续任务无法被检查，具备 head-of-line blocking 的结构性条件。但静态代码不能证明后续任务会更早 ready，也不能证明改变调度一定改善 TTFT 或吞吐。

GVA 路径的依赖链包含 save CPU event、save NPU event、attention gate 的 CPU record wait 和 gate NPU event；key-based 路径的依赖链不同。必须先把 host 等待、NPU 同步、backend 提交和完成拆开测量，再决定是否修改调度。

相关位置：

- `pool_worker.py:1672-1715`
- `kv_transfer.py:333,496-518,1231-1293,1545-1631`

### 调查任务

### 实现约束（仅在决定优化时适用）

- 不能绕过 attention boundary；不能在 save CPU/NPU event 完成前复用共享 buffer。
- 必须保留每层 load/save completion event、lease 生命周期、`request_queue.task_done()`、异常传播和 shutdown 语义。
- 同一 buffer owner 链和同一请求内存在真实数据依赖的任务不得乱序；无依赖任务才可越过未就绪队头。
- profiler/时间线关闭时不得在热路径保留高频字符串格式化、NPU 同步或无界内存记录。
