### 与 skill 原始流程的偏差（及原因）

1. **模型统一覆盖**：yaml baseline 引用 3 种模型（Qwen3-0.6B / Qwen3.5-4B / Qwen3-30B-A3B-w8a8），135 仅 0.6B 有 → 用 `--model` 覆盖。影响：MM/LoRA/Exception 部分 section 的"模型前提"不满足（见 §4 分类）。

## 8. 环境架构备忘（重要，避免复测误判）

**135 存在两个同名 `/mnt/weight`，视角不同内容不同：**

| 视角 | /mnt/weight 实体 | 内容 |
|---|---|---|
| 宿主机 shell（ssh 直连） | NFS4 172.27.1.31:/weight | 80 个模型（Qwen3-32B-W8A8 40G、Qwen3-30B-A3B-W8A8 30G 等全套） |
| 容器 pr15367_135 内 | 宿主机本地盘 /dev/nvme2n1p4 的 /mnt（bind mount 不传递 NFS 子挂载） | 仅 5 项：Qwen3-0.6B、Qwen3.5-4B（下载中）、qwen35-4b-text-only-sql-lora 等 |

**结论**：容器内跑 vllm serve 只能看见本地盘的 5 个资产；NFS 上的模型需 `docker cp`（或重新挂载）进容器。测试脚本（go.ps1 map_135）默认在**容器内**执行，而 `ssh root@80.5.9.135 "..."` 直连命令在**宿主机 NFS 视角**执行——两者 ls 同一路径结果不同，排查时务必先分清视角。

磁盘：本地盘 2.9T 用 97%（剩 ~91G），docker cp 43G（32B-W8A8 40G + EAGLE3 draft 3G）后剩 ~48G。
