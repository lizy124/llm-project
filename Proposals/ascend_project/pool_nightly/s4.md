## 1. 方案与思路

### 1.1 S4 的看护职责

S4 是全家族里唯一的 **MTP3 投机解码 × 池化** 交互载体：

- 模型 = DeepSeek-V4-Flash-W8A8 + `deepseek_mtp`（**num_speculative_tokens = 3**）
- 并行 = 单机 **TP8**（DP1）
- 池化 = memcache + `kv_both` + **`use_layerwise=false`**

看护目标有两类：

1. **接受率（精度侧）**：MTP3 的投机接受率是否被池化变量扰动 → baseline `0.925`，tolerance `0.05`
2. **吞吐（性能侧）**：perf baseline `90`，threshold `0.97`（首跑回填）
   - 两项都要在 **open / close 两个 case** 上各看一遍，共 4 组数字。

### 1.2 为什么是 open / close 两个 case

yaml 里两个 case 共用同一份 `_server_cmd`（含池化），只在 `server_cmd_extra` 的 `--additional-config` 上分叉：

| case | `enable_block_verify` | `enable_entropy_verify` | `enable_cpu_binding` |
|---|---|---|---|
| `deepseekv4-flash-w8a8-enable-open` | `true` | `true` | `"true"` |
| `deepseekv4-flash-w8a8-enable-close` | `false` | `false` | `"false"` |

对照意义：**验证池化叠加后，投机解码的两种拒采样配置都能正常起服与解码**，接受长度量级一致、无异常。

### 1.3 池化叠加方式（与 S3 的关键差异）

- S4 用 **anchor 复用**：`_kv_pool` + `_server_cmd` 定义一次，两个 case 同时挂 → 池化对两 case 同时生效。
- `use_layerwise=false`：S4 的 perf 负载（`GSM8K-in3500-bs2800`）**无共享前缀**，池只承担 **lookup 查询路径**，命中回读路径本就不该触发。
- 因此 S4 里 `kvpool hit tokens` **恒 0 是正常预期**（与 S3 的哨兵语义相反）。真正的哑失效监控在 S3 上。

### 1.4 与 S3 共用同一台机

S4 与 S3 都在 139 上，**共用 memcache 5000/6000 端口**，因此两者**不能同时跑**，必须串行；每次起服前先清残留并做端口预检。

### 阶段 0：前置预检（G0）

```bash
npu-smi info                                  # 确认 0~7 卡空闲
ss -ltn | grep -E ':(5000|6000|8600) '        # 有输出=冲突，先解决

```

### 阶段 1：起池 → 逐个 case 起服 → 发压 → 采集

脚本 `125-s4-run-139.sh` 的行为（对 `open` / `close` 各跑一遍）：

1. 清残留（`VLLM::` / `vllm serve` / 上一 case 的服务），起 memcache 池，等 5000/6000
2. 起 vLLM（本 case 的 `additional-config`），等 `/health`（预算 40 min）
3. **发压**：32 并发 × 每条 ~3500 token **独立前缀**（无共享前缀）请求，`max_tokens=256`、`temperature=0`
4. 采集：
   - `grep -aE "SpecDecoding metrics" logs/s4_${CASE}.log | tail -3`
   - `grep -ac "kvpool hit tokens" logs/s4_${CASE}.log`
5. 杀服务 → 进入下一个 case

### 阶段 2：池服务生命周期（G6）

每 case 起停各一次；case 结束后 `ss -ltn` 复核 5000/6000 已释放；关注 MetaService 是否异常退出、有无 OOM。

### 阶段 3：判卷（CI runner，服务器侧做不了）

`vllm-ascend/GSM8K-in3500-bs2800` 在服务器侧不存在，perf 与接受率的**判卷**必须在带数据集的 CI runner 上执行：

## 6. 本次（20260930）实测结果

**执行机**：139（8 卡，TP8）；**方式**：yaml 原样参数逐字复刻，串行跑两 case。

| 项 | case=open | case=close |
|---|---|---|
| 服务状态 | **READY** | **READY** |
| 请求成功率 | **32/32** | **32/32** |
| SpecDecoding `Mean acceptance length` | 2.48 → **2.64** | 2.38 → 3.06 → **2.71** |
| `kvpool hit tokens` 行数 | **0**（符合预期） | **0**（符合预期） |
| 池服务（MetaService 5000/6000） | 正常起停 | 正常起停 |

**判读**：

- open（`block_verify`+`entropy_verify`=true）与 close（均 false）**都能起服并正常解码**，接受长度量级一致（2.64 vs 2.71）。
- 说明 `memcache + kv_both + layerwise=false` 与 **MTP3** 共存无异常 —— 与 proposal「S4 特有增量 = DSV4 + W8A8 + deepseek_mtp + TP8」的预期一致。

**必须注意的指标量纲差异**：

- 本次采到的是 **`Mean acceptance length`**（每步接受 token 数，≈2.6）；
- yaml 判卷用的是 **`acceptance_rate`**（baseline `0.925`），由 runner 按 `test_content: spec_decode_acceptance` 计算，**两者量纲不同、不可直接比较**。
- 因此本次实测只能作为「机制通、服务稳」的观测，**接受率与 perf 数字不可比**。

**问题**：

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | nightly perf 数据集 `vllm-ascend/GSM8K-in3500-bs2800` 服务器侧不存在 | perf 与接受率无法在服务器侧产出可比数字 | 判卷走 CI runner |
| 2 | 自造 ~3500 token 负载替代数据集 | 与 nightly baseline 不可比 | 同上，仅作机制观测 |
| 3 | 单 case 起服约 10 分钟（280GB 权重），两 case 串行 | 单轮耗时较长 | 排期时预留 |
| 4 | 与 S3 共用 139 与 5000/6000 端口 | 不能并行 | 串行排期 |
